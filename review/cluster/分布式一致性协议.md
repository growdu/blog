# 审校：分布式一致性协议

- 原文：`docs/cluster/分布式一致性协议.md`
- 范围：全文
- 目标读者：想搞清「Paxos / Raft / ZAB / Totem 到底什么关系」的开发者
- 一句话定位：把四个协议放在一张关系表上，说明它们各自解决的是同一类问题的哪些部分，以及选型时该看谁
- 核心判断：这几个协议不是同一层次的替代品——Totem 解决的是**集群成员与有序广播**，Raft/ZAB 解决的是**状态机一致**；把它们并列为「四种一致性协议」会让读者做错选型
- 审校状态：已合入

## 优先修改

1. 位置：L9、L11、L15、L85 ——「二阶段提交」这个说法（**最严重的一条**）
   - 问题：正文把 Paxos 称作「二阶段提交」（L9）、把 Raft 称作「二阶段提交，基于 paxos 协议完善和改进」（L11）、把 ZAB 称作「二阶段提交」（L15），L85 又说 ZAB 的消息广播「类似一个 2PC 二阶段提交过程」。**Paxos 不是二阶段提交**：2PC 是带协调者的阻塞式提交协议（prepare + commit，participant 阻塞等决议），Paxos 是允许故障的多数派共识算法；Raft 和 ZAB 更是「Leader 复制日志 + 多数派 ACK + 提交点」，与 2PC 的协调者语义完全不同。这个错误会一路误导读者去理解 Raft 的选举与提交
   - 建议（已采用）：开头加一段「先厘清一个常见误解」把 2PC 与多数派共识的差别讲清；三处「二阶段提交」删除；ZAB 那处改为「形式上类似两阶段（提案 → 提交），但**不是** 2PC：它没有阻塞式协调者，quorum 决议不要求所有节点参与」
   - 原因：这是会直接导致错误理解的**术语性事实错误**。README 原则 1 说保真，但保真不等于保留错误——保留错误叫误导

2. 位置：L3-L17（开头列表）与 L19-L46（正文）
   - 问题：开头列表与正文**逐字重复**（L7 与 L21 的第一句完全相同）
   - 建议（已采用）：把开头列表升级成一张**关系表**（协议 / 解决的问题 / 代表实现 / 一句话定位），正文只保留展开
   - 原因：README 明确点名的「为凑完整而重复前文」。而这个列表本来可以升级成全文最有价值的东西

3. 位置：L21-L46、L50-L75、L79-L100（三个协议正文的全部）
   - 问题：**整段正文都是 markdown 引用块**（每行以 `>` 开头），渲染出来是引用样式，通常是整段粘贴自 CSDN 留下的痕迹。代价是：① 读者无法区分「作者自己的判断」和「引文」；② 文章没有作者自己的声音——与 README 原则 4「保留人的声音」相悖
   - 建议（已采用）：去掉粘贴留下的引用标记，改写成作者自己的叙述；只保留两处**新写**的引用块（开头「先厘清一个常见误解」与 Raft 那条「同步之前丢失的消息」的说法澄清）——它们是作者自己的补充，不是引文
   - 原因：这篇目前是「资料汇编」，不是「工程师的说明」

4. 位置：L56、L68（leader 选举）
   - 问题：三处具体缺陷：
     ① L56 写「如果 Follower 没有收到 Leader 的**心跳响应**超过 150—300ms」——方向反了：Follower 是**接收** Leader 的心跳，是 Follower 自己**收不到**心跳才触发选举超时。随机化（150~300ms）的目的也写反了：不是为了「让谁先竞选谁当选」，而是为了**减少 split vote**
     ② L68 写「其他节点收到竞选请求，会响应同意」——漏掉了 Raft 安全的核心：**Follower 只有在候选人的日志不比自己旧时才投票，且每任期最多投一票**
     ③ L68 写「去同步之前丢失的消息」——Raft 里 Follower 从不「丢失」已提交条目，冲突条目由 Leader 覆盖截断
   - 建议（已采用）：三处全部改写；投票规则补全为「本任期内还没投过票 + 候选人的日志至少和自己一样新」，并说明这两条正是 Leader Completeness 的根本；新增一个引用块澄清「丢失的消息」的说法
   - 原因：这是全文技术含量最高的一段，也是错得最多的三处

5. 位置：L89
   - 问题：「3. Leader若收到follower的半数以上ACK反馈；」——**句子不完整**（有主语没有谓语），且用分号结尾；「半数以上」与 L68 的「大多数（n/2 + 1）」口径不一致
   - 建议（已采用）：改写为「Leader 收到多数派（quorum，n/2 + 1）的 ACK 反馈后，确认该 Proposal 达到提交条件」，全文统一用「多数派（n/2 + 1）」
   - 原因：残句会让读者怀疑是复制粘贴没改完

6. 位置：L81「心跳方向相反」的说法
   - 问题：ZAB 的 Leader 同样向 Follower 发送心跳与 Proposal，方向并没有相反。真正的差别在**确认方向与流水线方式**（Raft 里 Follower 直接回 ACK；ZAB 里 Follower 把 ACK 放进各自 FIFO 队列，Leader 按序取走，形成 FACK 流水线）以及恢复阶段的选主方式
   - 建议（已采用）：改为「差异主要在确认方向与流水线方式，而不是心跳方向」，并补上 FACK 流水线这一机制；保留原文「ZAB 叫 epoch、Raft 叫 term」这种命名差异——那部分是对的，也是好细节
   - 原因：这句话把两个协议最容易被混淆的点说反了，读者会据此形成错误的心智模型

7. 位置：L102-L107（reference）
   - 问题：`# reference` 用的是 **H1**，与文章标题平级——渲染出来是两个顶级标题，破坏层级；四条 reference 里**两条是同一个 URL**（L106 与 L107 完全相同），且**全是 CSDN 二手博客**
   - 建议（已采用）：改成 `## 参考资料`；删掉重复的那条；换成一手来源——Raft 论文、ZAB 论文、totem/corosync 的原始描述与项目文档
   - 原因：二手博客当唯一来源，读者无法验证；四个协议里三个是一手论文定义的，引用一手来源是最低成本的准确性提升

8. 位置：三个协议小节
   - 问题：三个小节用同一套模板（定义 → 角色/阶段 → 要点），没有一处说「这个协议的代价是什么」「它在什么场景下不够用」
   - 建议（已采用）：补失效模式——totem 分区即脑裂且恢复后丢消息（原文已提但没展开）、Raft 网络分区下可能反复选举且依赖多数派可达、ZAB 依赖 FACK 流水线且 Leader 崩溃后需恢复协议选新；并在文末补「选型速查」表（需求 → 选谁 → 代价）
   - 原因：README 的「工程取舍」要素要求「方案的成本、风险、性能影响与适用场景，而不只给唯一最佳实践」——现在这篇恰恰只给了「是什么」

9. 位置：全文
   - 问题：缺「编写人 / 编写内容 / 编写时间」信息表（MET-01）；开头也没有一句话说清「本文回答什么」（STR-02）
   - 建议（已采用）：补信息表；开头改成「本文回答两个问题：**它们各自解决的是同一类问题的哪一部分**，以及**选型时该看哪个**」
   - 原因：README 要求「一句话定位」；这四条协议的关系正是读者真正需要的判断

## 事实待核

- [x] **Paxos / Raft / ZAB 与 2PC 的关系** —— 已核实。2PC 是带协调者的阻塞式提交协议；
  Paxos / Raft / ZAB 是多数派共识，无阻塞式协调者。正文已按此改写
- [x] **Raft 的投票规则** —— 已核实。Follower 投票的两个前提是「本任期内还没投过票」
  与「候选人日志不比自己旧」，这是 Leader Completeness 的前提（Raft 论文 §5.4.1）
- [x] **ZAB 的心跳方向** —— 已核实为**反的**：ZAB 的 Leader 同样向 Follower 发心跳与
  Proposal，差异在 FACK 流水线与恢复选主。正文已改
- [不适用] **totem 分区时的确切行为** —— 仍待核。文中「会脑裂，当网络恢复时会造成消息丢失」

  `wait_for_all` 行为误记成协议本身的行为。**本次未改动这句**——它涉及的是
