# 审校：分布式一致性协议

- 原文：`docs/cluster/分布式一致性协议.md`
- 范围：全文
- 目标读者：想搞清「Paxos / Raft / ZAB / Totem 到底什么关系」的开发者
- 一句话定位：把四个协议放在一张关系图上，说明它们各自解决的是同一类问题的哪些部分
- 核心判断：这几个协议不是同一层次的替代品——Totem 解决的是**集群成员与有序广播**，Raft/ZAB 解决的是**状态机一致**，把它们并列为「四种一致性协议」会让读者做错选型
- 审校状态：建议中

## 优先修改

1. 位置：L9、L11、L15、L85 ——「二阶段提交」这个说法（**最严重的一条**）
   - 问题：正文把 Paxos 称作「二阶段提交」（L9）、把 Raft 称作「二阶段提交，基于 paxos 协议完善和改进」（L11）、把 ZAB 称作「二阶段提交」（L15），L85 又说 ZAB 的消息广播「类似一个 2PC 二阶段提交过程」。**Paxos 不是二阶段提交**：2PC 是带协调者的阻塞式提交协议（prepare + commit，participant 阻塞等决议），Paxos 是允许故障的多数派共识算法；Raft 和 ZAB 更是「Leader 复制日志 + 多数派 ACK + 提交点」，与 2PC 的协调者语义完全不同。这个错误会一路误导读者去理解 Raft 的选举与提交
   - 建议：把三处「二阶段提交」全部换成准确说法——「Paxos 是多数派共识算法」「Raft 是把 Paxos 的角色拆成 Leader 选举 / 日志复制 / 状态安全三个子问题的工程化实现」「ZAB 的广播流程是 Leader 提案 + 多数派 ACK + Leader 广播 commit，与 2PC 的区别在于没有阻塞式协调者」；L85 那句改为「形式上接近两阶段：提案（prepare 阶段）→ 提交（commit 阶段），但 quorum 决议不要求所有节点参与，因此不会像 2PC 那样阻塞」
   - 原因：这是会直接导致错误理解的**术语性事实错误**。README 原则 1 说保真，但保真不等于保留错误——保留错误叫误导

2. 位置：L7 与 L21 ——开头列表与正文逐字重复
   - 问题：L7 的「totem协议，全称是 The Totem Single-Ring Ordering and Membership Protocol，是一个基于令牌环的分布式一致性算法。corosync 基于 totem 协议实现。」与 L21 的第一句**逐字相同**；L9/L11/L15 的列表项也在正文里有对应段落，读者等于读了两遍同一段开头
   - 建议：把 L3-L17 那个列表改成一张**真正的关系表**（协议 / 解决的问题 / 谁在用 / 是否容忍脑裂 / 成员变更怎么做），正文只保留展开；或者干脆删掉列表，用一段话交代四个协议的关系
   - 原因：README 明确点名的「为凑完整而重复前文」。而且这个列表本来可以升级成全文最有价值的东西——一张对比表

3. 位置：L21-L46、L50-L75、L79-L100（三个协议正文的全部）
   - 问题：**整段正文都是 markdown 引用块**（每行以 `>` 开头），渲染出来是引用样式。这通常是整段粘贴自 CSDN 等外部博客留下的痕迹，代价是：① 读者无法区分「作者自己的判断」和「引文」；② 文章没有作者自己的声音——这与 README 原则 4「保留人的声音，不把文章统一改成模板腔」相悖；③ 列表、代码块在引用块里的渲染也容易走形
   - 建议：去掉引用标记，改写成作者自己的叙述；确实要引用他人观点的地方，单独用一处引用块标出来即可
   - 原因：这篇目前是「资料汇编」，不是「工程师的说明」。README 的个人 IP 定位要求文章读起来像「有经验的工程师在清楚地说明问题」——引用块铺满全文正好是反面

4. 位置：L68（leader 选举）与 L102-L107（reference）
   - 问题：三个具体缺陷：
     ① L56 写「如果 Follower 没有收到 Leader 的**心跳响应**超过 150—300ms」——方向反了：Follower 是**接收** Leader 的心跳，是 Follower 自己**收不到**心跳才触发选举超时。选举超时的随机化（150~300ms）也说反了因果：随机化是为了**减少多个 Candidate 同时发起选举造成 split vote**，文中却说成「这样就是想谁先发出竞选，谁当选 leader」
     ② L68 写「其他节点收到竞选请求，会响应同意」——漏掉了 Raft 安全的核心：**Follower 只有在候选人的日志不比自己旧时才投票，且每任期最多投一票**。这条规则正是 Raft 能保证 Leader Completeness 的原因，漏掉它，读者会以为 Raft 的选举是多数人举手表决
     ③ L68 写「挂掉的节点……会发现自己的 term 小于最新的，此时就会切换到日志复制，去同步之前丢失的消息」——Raft 里 Follower 从不会「丢失」已提交条目；冲突条目由 Leader 用日志复制覆盖截断
   - 建议：把这三处分别改写为准确表述，并在 L68 后补一句投票规则：「Follower 收到 RequestVote 后，只有当候选人的日志**至少和自己一样新**、且自己在本任期内还没投过票时才同意」
   - 原因：这是全文技术含量最高的一段，也是错得最多的三处。选举规则讲不清，整篇「一致性协议」科普就立不住

5. 位置：L89
   - 问题：「3. Leader若收到follower的半数以上ACK反馈；」——**句子不完整**（有主语「Leader若收到…反馈」却没有谓语），且用分号结尾。下一条 L90 才是「Leader 向所有的 follower 发送 commit」，所以第 3 条应该是「Leader 收到多数派 ACK 后，确认该 Proposal 可以提交」
   - 建议：改写为「3. Leader 收到多数派（quorum）的 ACK 后，确认该 Proposal 达到提交条件」，并把「半数以上」统一成「多数派（quorum，N/2+1）」——全文 L68 的 Raft 选举里已经用了「大多数（n/2 + 1）」，两处口径要统一
   - 原因：残句会让读者怀疑是复制粘贴没改完

6. 位置：L102-L107
   - 问题：`# reference` 用的是 **H1**，与文章标题 `# 分布式一致性协议` 平级——渲染出来会变成两个顶级标题，破坏层级；同时四条 reference 里有**两条是同一个 URL**（L106 与 L107 都是 `.../article/details/106510970`）
   - 建议：改成 `## 参考资料`；删掉重复的那条；并把四条 CSDN 链接换成一手来源——Raft 论文（Ongaro & Ousterhout, *In Search of an Understandable Consensus Algorithm*）、ZAB 论文（Junqueira, Balakrishnan, Andersen, *A Simple Quorum-Based Protocol for Asynchronous Fault-Tolerant Consensus*）、totem 协议原始描述（Barrett & Williams, *A Token Ring Approach to Network Protocol Management*）、以及 corosync 的文档
   - 原因：二手博客当唯一来源，读者无法验证；四个协议里三个是一手论文定义的，引用一手来源是最低成本的准确性提升

7. 位置：L19、L48、L77 三个协议小节
   - 问题：三个小节用的是**同一套模板**（定义 → 角色/阶段 → 若干条要点），且没有一处说「这个协议的代价是什么」「它在什么场景下不够用」
   - 建议：每个协议补一段「它的失效模式」：totem 在分区时脑裂且恢复后丢消息（L21 已经提到但没展开）；Raft 在网络分区下可能反复选举、且依赖多数派可达；ZAB 依赖 FACK 流水线且 Leader 崩溃后需要恢复协议选新 Leader
   - 原因：README 的「工程取舍」要素与「踩坑与校验」要素都落在这里。只讲「它是什么」的协议科普，读者读完仍然不知道怎么用

8. 位置：L81「Raft为了保证日志连续性，心跳方向为Leader至Follower，ZAB则相反」
   - 问题：ZAB 的 Leader 同样向 Follower 发送心跳与 Proposal，方向并没有相反；两者真正的差别在**确认方向与流水线方式**（Raft 是 Follower 周期性直接回 ACK；ZAB 是 Follower 把 ACK 放进各自的 FIFO 队列，再由 Leader 从队列里按序取走，形成 FACK 流水线），以及**恢复阶段的选主方式**
   - 建议：改写为准确表述，并保留 L81 那句「ZAB 叫 epoch、Raft 叫 term」这种命名差异——那部分是对的，也是好细节
   - 原因：这一句把两个协议最容易被混淆的点说反了，读者会据此形成错误的心智模型

## 事实待核

- L9/L11/L15 的「二阶段提交」定性：本记录判断为术语性错误，但**具体改写措辞**需要按 ZAB 与 Raft 原论文的术语逐句对照后再定，尤其是「Raft 是 Paxos 的简化/衍生」这一说法在论文里的原始表述（Ongaro & Ousterhout 明确说 Raft 不用 Paxos，但结构上同源）
- L56 的 150—300ms：需要确认这是 Raft 论文的选举超时建议区间，还是特定实现的默认值；文中把它当成通用值写，需标注来源
- L21 的 totem 描述（「totem 会脑裂，当网络恢复时会造成消息丢失」）：需对照 corosync/totem 原始论文确认脑裂时的确切行为，避免把 corosync 的 `wait_for_all` 行为误记成协议本身的行为
- L21 的四个阶段（Gather / Commit / Recovery / Operational）：这是 totem 的 membership 阶段划分，需确认与原始文献中的命名一致（Gather / Commit / Recovery / Operational 之外的 "membership view change" 术语在不同版本里有出入）
- L85「ZAB 消息广播类似 2PC」：ZAB 论文里的表述是 "atomic broadcast"，与 2PC 的关系需要按论文措辞核对后再决定改成什么

## 可补的技术证据或产物

- 机制 / 源码入口：文章目前是纯概念，没有落到任何实现。cluster 支柱里有 `docs/cluster/raft/`、`docs/cluster/DCF/` 等源码向内容，可以补一句「openGauss DCF 的实现见……」把概念与自家实现连起来；Raft 可以对照 etcd 的 `raft` 包
