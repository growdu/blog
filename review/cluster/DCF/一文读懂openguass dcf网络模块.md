4. 位置：L1624 与 L1641（接收与发送定位 channel 的写法几乎逐字相同，
   而差别被藏住了）
   - 问题：检查器 AIF-05 报 0.96——两句只差一处：
     - L1624（接收）：「……包含的 stream_id 和 **src_inst** 可以确定一个channel……」
     - L1641（发送）：「……包含的 stream_id 和 **dst_inst** 可以确定一个channel……」
     差别藏在最后三个字母里，而再往下的**代码差别更大**：
     - 接收（L1627）：`channel = &mec_ctx->channels[head.src_inst][head.stream_id];`
       —— 第二维**直接用 stream_id，没有取模**；
     - 发送（L1646-L1648）：
       `channel_id = MEC_STREAM_TO_CHANNEL_ID(head.stream_id, profile->channel_num);`
       即 `stream_id % channel_num`，然后 `channels[head.dst_inst][channel_id]`
       —— 第二维**取了模**。
     → 两条路径对同一维度用了两套下标算法。发送侧既然要取模，就说明
     stream_id 可以 ≥ channel_num；那接收侧直接拿 stream_id 当下标就越界了
     （`channels` 第二维是 `MEC_MAX_CHANNEL_NUM`，见 L228 的
     `is_connect[CM_MAX_NODE_COUNT][MEC_MAX_CHANNEL_NUM]`）。
     → 唯一说得通的情况是：**发送侧在组包时把 `head->stream_id` 改写成了
     channel_id**。若确实如此，两处都该写清楚（发送侧「改写成 channel_id 后
     发出」、接收侧「stream_id 已是 channel 编号」），否则读者照抄这段代码
     会踩坑；这不是排版问题，是**语义被两句雷同的话盖住了**。
   - 建议：把两句改成一张对照表（发送 / 接收 × 用哪个字段 × 下标怎么算），
     并写明 stream_id 与 channel_id 的换算发生在哪一步。**定稿前请拿 openGauss
     源码 `contrib/dcf` 里 `mec_proc_recv_msg` 与发送侧组包的位置对一遍。**
   - 原因：涉及代码正确性，必须可回溯。
