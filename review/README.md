# 博客内容审校（review）

这里存放对 `docs/` 中博客内容的审校任务、修改建议与复盘记录。

目标不是把文章改得更华丽，而是让它读起来更像一位有经验的工程师在清楚地说明问题：
具体、自然、有判断，也保留原文的技术准确性和个人风格。审校还应当让每篇文章
有足够的技术密度、可验证性与辨识度，逐步形成 growdu 的个人专业品牌。

## 审校原则

1. **先保真，再润色。** 不改变技术结论、数据、引用、命令、链接或作者立场；拿不准的事实标为待核实，不靠改写补全。
2. **按读者的阅读路径组织。** 先说明问题、背景和结论，再展开原理、步骤与边界；删掉读者无需知道的铺垫。
3. **让抽象话落地。** 优先用具体对象、条件、行为和结果，少用空泛评价。
4. **保留人的声音。** 保留有价值的经验、犹豫、取舍和失败案例；不把文章统一改成模板腔。
5. **小步可审。** 每次只处理一篇或一个明确章节，建议应能逐条确认和回滚。
6. **用证据建立技术感。** 技术感来自源码、实验、日志、指标、版本差异和取舍，
   不来自堆术语或把简单问题说复杂。
7. **写出自己的工程判断。** 除了“是什么”，尽量说明“为什么这么做、别的方案为什么
   不选、什么条件下结论会失效”。

## 技术深度检查

一篇技术文章不必面面俱到，但应至少具备下列要素中的两到三项：

- **问题边界**：版本、系统规模、前置条件、本文不讨论什么。
- **机制解释**：从调用链、数据流、状态变化或关键数据结构解释“为什么”。
- **可复现证据**：SQL、命令、最小示例、日志、压测方法或源码定位。
- **工程取舍**：方案的成本、风险、性能影响与适用场景，而不只给唯一“最佳实践”。
- **踩坑与校验**：常见误解、失败路径、如何观察和验证结果。

审校时优先补“读者因此能做什么”，而不是扩写背景。例如，把“需要注意并发问题”
改成并发在哪个临界点发生、怎样复现、观测什么指标、该选什么规避方案。

## growdu 个人 IP 的内容策略

growdu 的差异化不应是泛泛的“技术博主”，而是围绕数据库内核、分布式系统、
高性能网络与长期工程实践，提供能落到机制和现场的中文技术解释。

每篇文章可视情况完成以下四件事：

1. **一句话定位。** 开头讲清楚文章替读者解决什么难题，以及为什么值得现在读。
2. **一个可记住的判断。** 用清晰、可证伪的观点串起全文；避免为了吸引注意而夸大。
3. **一份可带走的产物。** 结尾给出排查清单、决策表、实验命令、源码入口或延伸阅读。
4. **一条自然的内容路径。** 链向上一篇基础文章、相关实战或系列目录，让读者知道下一步看什么。

适合长期沉淀的内容支柱：

| 支柱 | 读者获得 | 推荐表达 |
| --- | --- | --- |
| 数据库内核与 PostgreSQL/openGauss | 从表象走到事务、WAL、执行器与复制机制 | 源码导读、机制图、实验复现 |
| 分布式一致性与存储 | 理解多数派、状态机、故障恢复与工程边界 | 反例、时序、决策取舍 |
| 高性能网络与系统工程 | 把 DPDK/VPP、Linux 和性能调优接到真实工作负载 | 指标、火焰图、排障记录 |
| 工程成长与工具实践 | 将复杂技术转成可执行的学习和交付方法 | 路线图、模板、复盘 |

“营销”在这里指帮助对的人发现、理解并持续信任内容：标题和摘要应准确承诺收获，
开头尽快进入问题，系列文章互相连接，案例与实验支撑可信度。不得使用标题党、
伪造案例、制造焦虑或把尚未验证的观点包装成结论。

## 常见“AI 味”信号

- 用“首先、其次、最后”“值得注意的是”“总而言之”等连接词堆砌结构。
- 反复强调“高效、全面、显著、至关重要”等结论，却没有条件或证据。
- 一段塞进多个结论，没有示例、因果关系或适用边界。
- 为凑完整而重复前文，或用泛泛的总结收尾。
- 把不确定的推断写成确定事实，或把工具、版本和场景抹平。

对应的修改方法通常是：删去重复句；补上“谁、在什么条件下、做了什么、结果如何”；把大段概述拆为短段；用原文已有的代码、日志或案例支撑判断。

## 可读性、布局与图表

前面几节管的是「说得对不对、说得实不实」。这一节管的是「读者读不读得下去」。
它以人读为主——检查器只能标出最机械的几处（图太大、引用离图太远），
其余的靠人判断。

### 四条人工要求

1. **有趣。** 开头给一个具体场景或一个反直觉的结论，让读者有理由往下读；
   中途给一次「原来是这样」的转折；结尾留一个能自己动手验证的入口。
   「有趣」不是加段子、不是用感叹号，而是**读者被承诺的回报被兑现了**。
   从头到尾只有正确结论、没有意外也没有细节的文章，是准确，但不好读。
2. **布局合理。** 信息的顺序要跟读者的疑问顺序一致：先问题，再边界，
   再机制，再证据，最后是取舍与产物。同一层级的内容放在同一层级，
   并列的两件事不要分居两节。目录能看出骨架；读者翻到任何一节都知道自己到了哪一步。
3. **可读。** 句子短，术语先解释后使用，缩写第一次出现给全称，
   一段只讲一件事，关键结论不要埋在长段落中间。
   读者中途不需要回读上一段才能接上下一段。
4. **简洁。** 删掉重复的、删掉正确但无用的常识、删掉「为了显得完整」而写的话。
   简洁不是短，是**没有一句是多余的**。删到删不动为止。

### 图表：太长就该拆

流程图和架构图最容易失控：加一个分支不用改文字，图就多一层；
作者顺着源码想的时候记得住十步，读者看图时记不住。

判据（机械可判，检查器实跑；阈值与 `tools/review-check.py` 的常量一一对应，
改一处必须改另一处）：

| 规则 | 指标 | 阈值 | 为什么是这个数 |
| --- | --- | --- | --- |
| `FIG-01` | 一张图里的框数 | 超过 15 个 | 到这个量级读者已经没法一眼扫到全貌，只能在框里找关系 |
| `FIG-01` | 顺着一路走的步数 | 超过 8 步 | 再长就要往回翻才能接上前后，起点和终点对不上 |
| `FIG-01` | 一个框分出的支线 | 超过 6 条 | 布局已经散了，视线要在同一个点上来回跳 |
| `FIG-01` | mindmap 的内容行数 | 超过 20 行 | 摊开这么长，已经不是导图是目录 |
| `FIG-02` | 「下图 / 上图」离图的距离 | 超过 10 行 | 读者会以为漏看了什么，图要紧跟在引用它的那一段后面 |

超限**不等于画错了**，而是说这张图该拆：按「一段一件事」拆成几张，
每张配一句话说明它在讲什么。拆的时候沿**语义边界**切（哪一步之后状态变了），
不要按框数均分——均分出来的两张图，仍然各自说不清一件事。

位图（PNG/JPEG）暂不做机械判定：图片的尺寸、比例、分辨率要人看。

## 每篇文章的审校流程

1. 确认原文路径、目标读者与本轮范围。
2. 先列出问题：表达不自然、结构跳跃、信息重复、论断缺乏边界、术语不一致，
   以及缺少机制、证据、取舍或可执行产物的位置。
3. 给出可直接采用的逐段建议，必要时提供改写前后对照；技术补充必须注明需要的依据。
4. 检查定位：标题、开头、核心判断、结尾产物和系列链接是否形成一致的读者路径。
5. 检查可读性：布局是否跟读者的疑问顺序一致，图表是不是太长该拆，
   段落是不是各自讲一件事，有没有删得掉的话。
6. 复核：技术事实、命令、链接、标题层级和作者原意均未被误改。
7. 在本目录留下简短记录；只有确认后的正文修改才进入 `docs/`。

## 审校记录模板

新建记录时，建议以文章 slug 命名，例如 `review/db/postgresql-xxx.md`：

```md

- 原文：`docs/…/文章.md`
- 范围：全文 / 第 N 节
- 目标读者：
- 一句话定位：
- 核心判断：
- 审校状态：建议中 / 已确认 / 已合入

## 优先修改

1. 位置：
   - 问题（类别）：
   - 建议：
   - 原因：

## 事实待核

## 可补的技术证据或产物

- 机制 / 源码入口：
- 实验或观测：
- 工程取舍：
- 结尾清单或下一篇链接：
```

### 「问题（类别）」怎么写

「优先修改」每条建议的**问题**一行以类别开头，写成 `- 问题（类别）：一句话描述`。
类别固定这五个——写不出来的，多半是问题还没想清楚：

| 类别 | 指的是 |
| --- | --- |
| 结构 | 章节顺序、层级、该拆该合 |
| 表达 | 句子、术语、语气、AI 味 |
| 事实 | 数据、版本、引用、链接 |
| 图表 | 图太长该拆、图与正文对不上、引用离图太远 |
| 可读性 | 趣味性、布局、可读、简洁 |

「可读性」这一类由人判断，检查器帮不上忙：它能标出「这张图有 18 个框」，
但说不出「这篇读起来闷」。

### 「事实待核」怎么写

每条待核事实用三种标记之一，机器从这三行解析：

| 标记 | 含义 | 阻塞「已合入」 |
| --- | --- | --- |
| `- [x] 事实` | 已核实，依据写在条目里 | 否 |
| `- [不适用] 事实` | 该事实涉及的正文本次没改，原文保留 | 否 |
| `- 事实` | 还没销掉 | **是** |

「已合入」的语义是：**与本次改动相关的**待核事实都销掉了，不是全篇事实都核实过。
所以标「不适用」是合法的——核不完、而本次又没碰它，就不该卡住合并。
（进度表里这两类分开记：「待确认」是没销掉的，「不阻塞」是标了「不适用」的。）

## 边界

- `review/` 只记录审校过程和建议，不是对外发布内容。
- 涉及事实、数据、版本、引用或外链的修改，必须可回溯到原始依据。
- 不为“去 AI 味”而删除必要的定义、前提、警告或操作步骤。
