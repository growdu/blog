7. 位置：L332-L336（Python `open()` 说明）

       行缓冲。整段是 Python 2 时代的说法。
   - 建议：按 Python 3 文档重写这一小节，并补上现在最该用的 `with open(...) as f:`

8. 位置：L353-L367、L408-L422（Python 读写与属性表）

9. 位置：L441（shell 删除目录下所有文件夹）

## 事实待核

- [x] Python `open()` 的默认 mode —— 实测 `open.__doc__` 与 `f.mode` 均为 `'r'`
  （只读），**不是**原文写的「默认为追加」。追加必须显式 `'a'`。
- [x] Python 3 有没有 `file.next()` —— 实测 `hasattr(f, 'next')` 为 `False`；
  Python 3 用 `next(f)`。`file.isatty` 实测是方法（`callable(f.isatty)` 为
  `True`），不是属性。
- [x] `struct stat` 里有没有 `st_off` —— 实测 `os.stat()` 结果中无 `st_off`，
  有 `st_size`；`st_blocks` 实测值 8 对应 4096 字节（`8 × 512`），确认单位是
  512 字节而非字节数。
- [x] bash 的 `if [-e $filename]` —— 实测报 `bash: [-e: command not found`；
  `if[! -s $filename]` 实测报 `syntax error near unexpected token 'then'`。
  两处都得在 `[` 后加空格。
- [x] bash 里的中文全角引号 —— 实测 `readpath=“/tmp/fqtest”` 后
  `$readpath/*` 匹配不到文件，循环只执行一次且变量是字面量 `“/tmp/fqtest”/*`。
  不报错，结果全错。
- [x] Java 缓冲流的方法名 —— 用 JDK 17 反射核对：`BufferedReader` 有
  `readLine`、无 `ReadLine`；`BufferedWriter` 有 `newLine`、无 `NewLine`。
- [x] Java `File.createNewFile()` 的父目录 —— 实测父目录不存在时抛
  `IOException: No such file or directory`。
- [x] Java `File.mkdir()` 与 `mkdirs()` 的区别 —— 实测多层目录下 `mkdir()`
  返回 false、`mkdirs()` 返回 true。
- [x] Java `char` 的大小 —— 实测 `Character.BYTES = 2`、`Character.SIZE = 16`，
  原文「字符(2byte=16bit)」成立。

## 可补的技术证据或产物

- 机制 / 源码入口：把整篇的骨架换成一条主线——「文件名 → inode → 数据块」的
  查找，加上「用户态缓冲 → `read(2)` 系统调用 → page cache → 落盘」这条链。
  C 的 `open`/`read`/`write`（POSIX）与 `fopen`/`fgetc`（stdio，缓冲在用户态）
  是两套东西，正文现在把 `fopen` 当成了「打开文件」的全部。Java 侧对应
  `java.io.FileDescriptor` / `FileChannel`，Python 侧对应 `io.BufferedReader`
  的缓冲层。给出这几个源码入口，读者才有「出事时去哪看」的抓手。
- 实验或观测：用 `strace -e openat,read,write` 看一次 `cat` 与一次用
  stdio 写文件的差别——stdio 的 4K/8K 缓冲会把多次小写合并成一次 `write`，
  这是 AIF-02「提高了读写的效率」唯一有说服力的证据形式（比直接给结论好）。
  再用 `lsof` 或 `/proc/<pid>/fd` 观察 Python 不写 `with` 时的句柄泄漏。
- 工程取舍：C 里什么时候该绕过 stdio 直接用 `read`/`write`（大文件顺序读、
  要精确控制写入边界）；Python 为什么从 `os.path` 走向 `pathlib`；
  Java 的 `File` 类为什么被 NIO 的 `Path` 取代（旧 `File` 只是路径的包装，
  真正的 I/O 在别处）——这些是「为什么」，比 API 清单更值钱。
- 结尾清单或下一篇链接：结尾给一张「操作 → C / Java / Python / shell」的
  速查表（现在散在四节里，读者要自己拼），再链到本仓库讲持久化与
  `fsync` 的文章——那才是与 growdu 定位真正接得上的下一篇。
