> **状态**：设计已确认（2026-11-11），待实现。
>
> **上游契约**：[../../publish/spec/00-架构设计.md](../../publish/spec/00-架构设计.md)（整体架构）、

## 一、目标与边界

### 1.1 一句话

把博客母稿裁成**头条版**（3K 精简稿 + 最多 3 张图，0 张也行），
在 `manual` 档产出发布包交人工上传；账号拿到 API 权限后，同一套代码改为直接调接口。

### 1.2 做什么

| 做 | 不做 |
| --- | --- |
| 按头条规则裁剪正文、重写标题、选图、转 webp、裁封面 | 不做视频（视频是 AIV 与视频号的事） |
| 产出发布包 + 发通知 | 不做定时调度（调度在 `publish/publishkit/`） |
| 调 API 建草稿 / 发表（拿到权限后） | 不做 Cookie 浏览器自动化（见 06 §6.8） |
| 维护自己的幂等状态 | 不改 `weixin/`，不改 `publish/publishkit/` |

### 1.3 硬边界

1. **不 import `weixin/`，不 import `publish/` 的包。** 接缝只有 TOML 与 manifest JSON。
2. **不做静默成功。** 每个「成功」都必须是显式确认过的成功。
3. **超限跳过并记录原因**，不做静默截断。
4. **凭据永不入库**（`toutiao/.gitignore` 已挡 `secrets.json`）。
5. **发布在本地执行**（与公众号同因：平台侧有 IP / 凭据约束）。

## 二、模块划分

形状照抄 `weixin/wechat/`（8 个模块 + CLI），但**模块名按头条的语义重排**：

| 模块 | 职责 | 对应 weixin |
| --- | --- | --- |
| `capability.py` | 能力模型读取：`publish/capabilities/toutiao.toml` 的限额与自动化档位 | 新增（weixin 无对应模块） |
| `contract.py` | 头条版切片规则：读母稿 → 产出版本（标题 / 摘要 / 正文 / 选图） | `posts.py` 的合格性判定 |
| `render.py` | 头条 HTML 渲染（inline style、无 class、代码块高亮） | `render.py` |
| `assets.py` | 图片转 webp、压缩到 ≤5MB、封面裁 3:4 ≥600×800 | `assets.py` |
| `publish.py` | 调开放平台接口，或产出发布包 | `publish.py` |
| `state.py` | 幂等状态 | `state.py` |
| `notify.py` | 通知 | `notify.py` |
| `cli.py` | 命令行入口 | `cli.py` |
| `mdparse.py` | Markdown 解析（front matter + 正文） | `mdparse.py` |

**不新建 `highlight.py` / `mermaid.py`**：头条版只有 3K，代码块与图表会显著稀释信息密度。
切片规则里直接**丢弃代码块与图表**，只留文字结论与必要的示意图。
（若实测发现技术号读者仍需要代码，另议——但默认不做。）

## 三、切片规则（本文的核心）

### 3.1 输入

母稿来自 `source/_posts/`（由 `tools/sync-hexo.py` 生成），
front matter 里有 `title` / `description` / `tldr` / `difficulty` / `platforms` / `publish_on`。

### 3.2 输出（头条版）

| 字段 | 规则 | 来源 |
| --- | --- | --- |
| 标题 | **≤ 30 字**，带数字或反常识 | 平台限额 +《运营手册》§2.3 |
| 摘要 | `description` → `tldr` → 正文首段 → 文章标题（兜底）；超 120 字裁到 120 字并记 note | 平台限额 |
| 正文 | **3000 字左右**（`body_chars = 3000`） | 《运营手册》§2.2「头条号图文 3K」 |
| 开头 | **第一段就抛结论** | 《运营手册》§2.3（头条是信息流，读者不读第二段） |
| 小标题 | 段落之间必须有 `##` 级小标题 | 《运营手册》§2.3（手机屏阅读靠小标题续命） |
| 正文图 | **最多 3 张**，webp，≤5MB；**0 张也能发**（头条有无图模式）——「1~3 张」是《运营手册》的写作建议，不是平台限额 | 平台限额（webp ≤5MB）+《运营手册》§2.3（张数建议） |
| 封面 | 单张竖图，3:4，≥600×800；**来源 = 正文第一张图**，没有正文图就不生成封面 | 平台限额 |
| 站外链接 | **正文里没有可点击 URL**，只留纯文本「完整版见 growdu.cn」 | 见 §3.4 |

### 3.3 图：最多 3 张，0 张也行

头条**不能用外链图片**——正文里的 `<img src="https://...">` 不生效，
图必须在编辑器里重新上传。这意味着每张图都是一道**人工工序**。

图越少，这道工序越省。而 3K 精简稿本来就只需要 1~3 张图——
**「图少」和「稿短」是同一条规则的两面**，不是两条。

**但「1~3 张」是《运营手册》给的写作建议，不是平台硬限额。**
平台真正的硬约束只有两条：

| 硬约束 | 什么时候适用 |
| --- | --- |
| 正文图 webp、≤5MB | 有图时 |
| 封面 3:4、≥600×800 | **上传封面时** |

头条允许**零图发布**（无图模式）。所以口径是：

- **切片规则只管「最多 3 张」**：正文里第 4 张及以后不收（连占位符一起删，记 note）；
- **不给没有图的母稿硬造图**：561 篇母稿里 542 篇可发布，其中 **469 篇本来就没有正文图**。
  造一张占位图只是把「这篇没图」这件事藏起来，读者看到的是一张没信息量的图；
- **封面来源 = 正文第一张图**（已转好的 webp 再裁 3:4）；**没有正文图 → 不生成封面**；
- **没有封面时，出包清单里那一行要明写**：
  「这篇没有正文图：按头条的『无图』模式发布；若后台强制要封面，需人工另配」——
  **不静默、不假装有**。

> **Task 4 / Task 6 按这一节实现**：选图、转 webp、裁封面、出包清单。
> 别按「每篇都要有图」设计流程——那会在 469 篇上落空。
>
> 落地时守住这四条：
>
> 1. **封面 = 正文第一张图**，裁的是**已转好的 webp**（不是原始 PNG），
>    裁完仍要 ≥600×800；不够就不生成封面，不硬造。
> 2. **外链图不下载**：出包不依赖网络，远程图在出包清单里列为「需人工下载」并附 URL。
> 3. **图路径解析不到就报错**，错误里带上那个路径——静默丢图会让出包缺图却没人知道；
>    解析结果必须留在站点根目录之内。
> 4. **没有正文图照样出包**：清单的封面那一行明写「这篇没有正文图：按头条的『无图』模式发布；
>    若后台强制要封面，需人工另配」。

### 3.4 链接降级（三重约束叠加）

1. 平台明令禁止「外链跳转代码」；
2. 正文插入外链属于头条的**独立创作者权益**，要单独开通，未开通时 URL 不会变成链接；
3. 头条号**简介里不得包含网站链接、邮箱或其他联系方式**——也不能挂在简介上。

所以：

- **正文末尾**：纯文本「完整版见 growdu.cn」（不带协议、不做超链接）
- **反方向由站点承担**：文章页的跨平台索引区块显示「已发布到头条号」+ 头条链接

**裸 URL 与 markdown 链接不是一回事。** 被降级的是 markdown 链接
（`[文字](url)`）——它带着链接标记，未开通「插入外链」权益时渲染出来
就是一段方括号加圆括号的乱码。正文里直接写的**纯文本 URL**
（`https://example.com`）不会变成可点击的链接：平台禁的是**外链跳转代码**，
不是 URL 这个字符串本身；权益没开通时，正文里的 URL 本来就只是文本。
所以切片规则只处理 markdown 链接，纯文本 URL 原样留着——
见到 URL 就当违规去乱改，会把正常的引用一起删掉。

> **这是公众号教训的同构复现。** 公众号实测「正文里的外链图片会被静默删除」，
> 读者看到的是一段突然断掉的正文。头条的「外链不生效」是同一个坑的另一个形状。
> **凡是把内容交给外部平台，就要逐条确认哪些元素会被吃掉，别假设。**

### 3.5 超限怎么办

**不是所有超限都跳过**：三类超限的处理不一样，别混。

| 撞上什么 | 怎么办 |
| --- | --- |
| 标题超 30 字 | **裁**到 30 字，标记「已裁剪」并进 note；**裁完一个字都不剩 → 跳过该篇**，记原因 |
| 正文超 3000 字 | **截断**到 3000 字（尾巴「完整版见 xxx」占的字先扣掉），标记 `body_truncated` 并进 note |
| 摘要超 120 字 | **裁**到 120 字，进 note |
| 图片超过 3 张 | **只保留前 3 张**，多余的连同占位符一起删掉，进 note |

**标题的处理顺序**：

1. 母稿有 `short_title` 字段 → 用它；它自己超 30 字 → **跳过该篇**，记原因
2. 否则从 `title` 裁到 30 字 → **但要标记「已裁剪」，进报告**
3. 裁完一个字都不剩 → **跳过该篇**，记录原因

**为什么标题跳过、正文截断**：标题是这篇的身份，裁坏了读者认不出是哪篇，
宁可不发；正文是内容，砍掉尾巴还能读，所以截断——但**把裁了多少写进 note**，
和摘要、图片一个口径。**任何裁剪都不静默。**

### 3.6 结构归一化：标题层级与列表

母稿的 Markdown 结构要**归一化**之后才进头条版。规则只有两条，但两条都是有意为之：

| 母稿里的写法 | 头条版输出 | 为什么 |
| --- | --- | --- |
| `##` 小标题 | `## 小标题` | 原样保留 |
| `###` 小节 | `## 小节` | **统一输出成 `##`** —— §3.2 的「小标题」行是头条版的阅读硬要求：段落之间必须有 `##` 级小标题。母稿的层级深浅是博客排版的需要，不是头条版需要的；照搬会让本来带小节的段落在小节化之后失去小标题 |
| `#` 一级标题 | **丢弃** | 它就是文章标题，已经在标题字段里；正文里再放一遍是重复 |
| `####` 及更深 | **丢弃** | 层级越深越细，3K 精简稿没有承载它的篇幅；§3.2 只承诺到 `##` 级 |
| `-` / `*` / `+` 列表项 | `- 列表项` | 列表项统一输出成 `- ` |
| `1.` `2.` 有序列表项 | `- 列表项` | 同上 —— 头条版不承诺有序语义 |

这两条是**行为**，不是碰巧如此：各有一条单元测试钉住
（`toutiao/tests/test_contract.py` 的 `test_heading_levels_are_normalized_to_h2`
与 `test_ordered_lists_are_normalized_to_dashes`），改坏了会红。

**附：摘要的兜底顺序与截断记录。** 摘要的取值顺序是
`description` → `tldr` → 正文首段 → **文章标题**。
最后一步是兜底：只在正文里一个段落都没有时才轮到它——
正文里只有图的母稿就是这种，这时候标题比「图占位符」有信息量得多，
也不会让上传包里出现一个「【图1】」这种看着像工具出错的半成品。
正文被过滤光了（整篇只有表格、引用、代码围栏）才跳过该篇并记原因。

摘要超过 `digest_chars`（120 字）会裁到 120 字，**并往 `notes` 里记一条**
「摘要已裁剪到 120 字」——与标题裁剪、正文截断一样，超限不静默丢字；
没超长时不添这条 note。

**列表项也可以当摘要**：正文第一块是列表项时，摘要取它的文字（去掉 `- ` 前缀），
不去跳过列表另找散文段落。这是有意的——「整篇只有列表」的母稿跳过去就只剩空摘要，
列表项的文字总比空着强。

### 3.7 行内与引用形态：同样要归一化

母稿里的东西不一定都是「独占一行」的正规写法。头条版只认自己那几样形态，
所以下面这些都要在切片时收拢：

| 母稿里的写法 | 头条版 | 为什么 |
| --- | --- | --- |
| 行内图片（`其架构如下图![](x.png)`） | 收进 `images`，正文里换成 `【图N】` | 行内图也是图，也得让人上传；不收的话正文里会留下字面量 markdown |
| 图路径带尾随标题（`![](x.png "图说")`） | 剥掉标题，只留路径 | 带标题的字符串不是路径，下载会失败 |
| 行内 HTML 标签（`<font color="red">文字</font>`） | 剥掉标签，**保留标签里的文字** | 标签是标记，文字是内容 |
| 纯 HTML 的一行（`<div class="x">`） | 整行丢弃，并断开段落 | 纯标记没有内容，跟表格、引用一样处理 |
| 不在白名单里的 `<xxx>`（`<db_oid>` `<relfilenode>` `<slug>`） | **原样保留** | 它们不是 HTML 元素，是路径与标识符里的占位符；剥掉就是发布错的技术事实 |
| 行内代码（`` `base/<db_oid>/<relfilenode>` ``） | **一个字都不动**（连里面的真标签名也不剥） | 反引号里是字面量。技术文里的路径、类型占位符几乎都在行内代码里，剥错了读者看到的是残缺的技术事实 |
| HTML 实体（`&amp;` `&nbsp;`） | **只在带标签的段落里**解码；行内代码里不解码 | 没标签的段落本来就不是 HTML，无差别解码会改掉原文 |
| 引用式链接（`[文字][1]`） | 降级成 `文字`，计入 `dropped_links` | 它也是链接；留着方括号是悬空标记 |
| 引用定义行（`[1]: https://…`） | 整行丢弃 | 那是链接定义不是正文，留着会把 URL 漏出去 |
| 空列表项（`1. ` 后面没内容） | 整行丢弃 | 否则会变成一段野段落（`"1."`） |

**「白名单」指真正的 HTML 元素**（`font` `div` `span` `br` `pre` `video` `iframe`
`table` `h1~h6` `p` `a` `ul` `ol` `li` `code` `strong` `em` …）。
**不在白名单里的 `<xxx>` 一律当普通文本**——宁可留着几个像标签的占位符，
也不能把 `base/<db_oid>/` 变成 `base/`。标签名**只认小写**：
`<Db_Oid>` `<FONT>` 都不是标签。头部元素（`title` `meta` `link` `base` `html`
`head` `body`）与读起来像普通词的名字（`slot` `data` `time` `output`
`summary` `param` `source` `object`）**不进白名单**——它们在这批母稿里
更常见的是占位符（`<slot_name>`、`<source_path>`、`<title>` 路径段）。

**行内图与独占行的图共用一套编号**，按正文顺序连续 —— 读者看到的
「【图1】【图2】」就是上传清单里的第 1 张、第 2 张。

## 四、出包结构（`manual` 档）

```
toutiao/out/<content_id>/
├── article.html        # 已按头条规则渲染
├── article.txt         # 纯文本备份（编辑器吃掉 HTML 时的兜底）
├── images/
│   └── 01.webp         # 正文图（已转 webp，≤5MB）
├── cover.webp          # 封面（3:4，≥600×800）
├── title.txt           # 标题（≤30 字）与摘要
└── README.md           # 人工上传步骤清单（对着打勾）
```

`README.md` 的内容固定为**人工动作清单**，每条都要能对着打勾：

```markdown
# 上传清单：<标题>

- [ ] 打开头条号后台 → 发文章
- [ ] 标题：复制 title.txt 第一行（≤30 字）
- [ ] 正文：article.html 粘贴到编辑器（若排版丢失，改用 article.txt）
- [ ] 上传 images/ 里的 N 张图，按顺序插入到第 N 个图片占位处
- [ ] 封面：上传 cover.webp
- [ ] 检查：正文末尾是纯文本「完整版见 growdu.cn」，不是超链接
- [ ] 发表
```

### 4.1 同时写状态快照

```
publish/outbox/<content_id>__toutiao.json
```

```json
{
  "content_id": "db/postgresql/...",
  "platform": "toutiao",
  "status": "packaged",
  "automation": "manual",
  "title": "逻辑复制大事务同步要 30 分钟？",
  "published_url": null,
  "package_dir": "toutiao/out/db-postgresql-...",
  "updated_at": "2026-11-13T09:00:03+08:00",
  "reason": "未认证账号无开放平台 API 权限，已出包待人工上传"
}
```

**`status = packaged` 不是「已发布」。** 站点索引要能区分这两种状态，
否则读者点进去发现没有这篇，等于把「发重了」的风险换成了「发虚了」。

## 五、幂等

三层键（与 `weixin/wechat/state.py` 同构，但**独立实现，不 import**）：

| 层 | 键 | 防的是什么 |
| --- | --- | --- |
| 内容 | 正文指纹 `sha256(body)` | 母稿改了 → 允许重发 |
| 平台 | `(content_id, platform)` | 同一篇重复出包 / 重复调接口 |
| 平台侧 | 头条返回的 `object_id` / `group_id` | 接口超时后重试不重复发 |

**超时不是失败。** 头条接口超时后，**先按 `object_id` 查一次状态再决定**——
直接重试可能发两遍。这条与公众号是同一条纪律。

## 六、CLI 契约

```bash
cd toutiao && python3 -m toutiao.cli scan                 # 盘点：哪些能发，为什么
cd toutiao && python3 -m toutiao.cli convert <slug>       # 切片 + 出包（不调接口）
cd toutiao && python3 -m toutiao.cli publish <slug>       # 出包 + 上传（API 权限开通后）
cd toutiao && python3 -m toutiao.cli status               # 查看状态
```

`<slug>` 是文章相对 `source/_posts/` 的路径去掉 `.md`，
例如 `db/postgresql/postgresql-logical-replication-add-guc`。

**退出码**（本模块自己的一份实现；取值与 `weixin/wechat/cli.py` 相同，

## 十、与 weixin/ 的关系：复制，不是共用

`toutiao/` 是从 `weixin/` 派生出来的**独立副本**。两边各改各的：

- **不共用代码**——没有公共模块，不互相 import
- **不做同步修复**——一边的修改不回流到另一边
- **不抽公共层**——平台规则本来就不同（头条标题 30 字、公众号 32 字），
  强行共用只会把差异藏进 if 里

所以：知道另一边有同样的问题，**由那一边自己处理**，
本模块既不跟踪、也不同步。本模块的行为以本目录的实现为准。

本模块自己这一边的既定行为：

| 事项 | 本模块的处理 |
| --- | --- |
| front matter 里的 `\"` 转义 | 按 YAML 语义还原（**仅双引号标量**，单引号不处理） |
| 未闭合的 front matter | 抛 `ValueError`，不当成「无 front matter」 |
| 不支持的母稿格式（如 `.html`） | `discover_unsupported()` 显式列出，不静默漏发 |

## 十一、标题转义还原：影响面
