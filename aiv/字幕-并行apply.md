## 二、口播稿（10 句，每行一句）

```
大家好，我是关注数据库内核方向的独立开发者。
前几期都在讲发布端，这期把镜头转到订阅端。
上游的并行 apply 是单事务内多流并行，事务之间还是排队。
排队不是最难的，难的是这几条事务能不能同时应用。
判据是它们有没有改到同一行，也就是有没有冲突。
有冲突的必须排在前面，没冲突的可以一起做。
所以要先看一个窗口，默认 1000 笔事务、10 秒或 1GB 先到就调度。
把事务之间的依赖画成一张图，按图的顺序分发出去。
最后按依赖顺序统一提交，提交的先后不能乱。
边界很清楚：这是我自己的设计方案，还没合进上游主线。
```

| 项 | 值 |
| --- | --- |
| 字数 | 251 字 |
| 句数 | 10 句 |
| 实际时长 | 待出片时实测（EP02 为 35.316 秒 / 267 字，本期 251 字） |

> 第 10 句是**边界声明**，也是人格规范 §5 要求的「什么时候不该用 / 不是谁的能力」。
> 这一期是全季唯一一期讲**作者自己未落地的方案**的，边界必须说在最后一句，
> 不能藏在字幕角落。

## 五、数据与机制出处

| 陈述 | 出处 | 状态 |
| --- | --- | --- |
| 上游的 `streaming=parallel` 是**单事务内**多流并行，事务之间仍是串行 | `docs/db/logical_decode/logical_parallel_apply/逻辑复制并行apply概要设计文档.md` §3.3、§11 | 上游公开机制，可引用 |
| 方案复用上游已有的 `ParallelApplyWorkerInfo` 与 `pa_launch_parallel_worker`，只加窗口调度层 | 同上 §3.3 | 上游公开机制 + 内部设计 |
| 冲突键由表、索引与键值构成（`relid` / `index_oid` / `key_values`） | `docs/db/logical_decode/logical_parallel_apply/逻辑复制并行apply依赖冲突检测设计文档.md` §4.1 | **内部设计文档** |
| 用 `last_writer` 做到 O(1) 判断「谁最后写过这个 key」 | 同上 §5.1、§5.2 | **内部设计文档** |
| 窗口内构造依赖 DAG，按拓扑序调度 | `逻辑复制并行apply概要设计文档.md` §8.1、§9.1、§9.2 | **内部设计文档** |
| 窗口默认 1000 笔事务 / 10 秒 / 1GB，三者任一达到即触发调度 | `docs/db/logical_decode/logical_parallel_apply/逻辑复制并行apply接口文档.md` §5.1、§5.5 | **内部设计文档**（文档另列 `transaction_parallel_min_transactions` 默认 5，为最小事务数门槛） |
| 提交顺序由提交协调器按 commit LSN 排序后逐个提交 | `逻辑复制并行apply概要设计文档.md` §10.1、§10.2 | **内部设计文档** |

> 方案已经实现或已经在生产环境跑过；窗口大小是上游的默认值。
> 画面上不出现设计文档内部的项目代号。
