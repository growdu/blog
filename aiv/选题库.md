## 一、第一季：机制族

**主线**：同一个机制往下挖——并行解码 → CSN 全序 → WAL 提交顺序 → 订阅端并行 apply → 结构化 DDL。

为什么是这条主线：

- **五期共用一套画面语汇**。时间线、缓冲区、图、队列、依赖边，本期已经画出来的
  「reader 协调 + 多 worker 并行」「按事务结束顺序输出」两张图，下一期直接接得上，
  不必每期重新设计版式。
- **观众是跟着一个机制往下走的**，不是每期换一个知识点。看完第一季，
  手里应该有「一个事务从 WAL 到订阅端落地的完整链路」这张地图。
- **口径可控**。五期都落在《人格规范》§3.1 的「逻辑复制与解码」「PostgreSQL 内核机制」

**口播骨架**（10 句，已定稿）

```text
大家好，我是关注数据库内核方向的独立开发者。
接着上期的问题：提交顺序到底是怎么定的？
并发时 commit 的先后是乱的，按时间戳排并不可靠。
openGauss 的做法是给每次提交发一个号，叫 CSN。
号从哪来？一个 64 位原子计数器，自增一号就归你。
所以不管谁先谁后，号的顺序永远和领取顺序一致。
这个号会写进 WAL 的提交记录，一路带到订阅端。
订阅端拿到号，就知道这条变更该不该先应用。
整个链路有六层保障，从计数器一直管到订阅端校验。
不过它的边界很清楚：这是 openGauss 的做法，不是 PostgreSQL 18 的能力。
```

```text
大家好，我是关注数据库内核方向的独立开发者。
上一期讲了提交顺序怎么定，这期往回退一步。
WAL 里的记录，是按谁先写进去排的，不是按谁先提交排的。
并发的事务写 WAL 会交错，几个事务的操作会穿插在一起。

所以发出去的顺序，是提交顺序，不是 WAL 的物理顺序。
```

**口播骨架**（10 句，草案）

```text
大家好，我是关注数据库内核方向的独立开发者。
前面几期都在讲数据的复制，这期讲结构怎么跟着走。
最直觉的做法是：DDL 写进日志，解码出来原样发给订阅端。
听着最省事，但社区讨论下来，这条路走不通。
问题在于订阅端只拿到一段文本，它没法判断这条命令到底做了什么。
所以方向是拆成结构化对象，分五步走：先捕获，再变成带语义的结构。

最后订阅端按语义执行，而不是拿到 SQL 就直接跑一遍。
这样才能支持改名映射，也能跨不同版本的数据库。
这套方案社区还在讨论，还没有合入主线的版本。
```

## 七、每期都要满足的硬指标

这些是选题阶段就要定的，不满足的题不要进这一季。

| 项 | 指标 | 出处 |

| 时长 | 30~35 秒 | `字幕-并行解码.md` 的目标时长 |

| 硬约束 | 不触禁词表、落在能力域内 | 《人格规范》§7 |
| 数字 | 每条陈述有出处，**实测数字必须带作者本人归因** | 《人格规范》§5 |

### 机检规则

规则实现在 `pipeline/pyv/topics.py`，编号必须与本表一一对应。

| 编号 | 级别 | 判据 |
| --- | --- | --- |
| `topics.structure` | 硬 | 每期必备字段齐全（id / 标题 / 主钩子 / 主线 / 能力域 / 状态 / 适配理由），关联文档 / 口播骨架 / 数字与出处三段都在 |
| `topics.doc-exists` | 硬 | 关联文档在仓库里真实存在 |
| `topics.no-hype` | 硬 | 标题与主钩子不命中《人格规范》的禁词表 |
| `topics.domain` | 硬 | 能力域名合法，且本期至少命中一个能力域（按《人格规范》§3.1 的关键词表判定） |
| `topics.sentence-count` | 硬 | 口播骨架恰好 10 句 |
| `topics.word-count` | 硬 | 口播骨架总字数 230~280（各句原始长度求和，含标点与空格） |
| `topics.sentence-width` | 倾向 | 单句显示宽度 ≤ 40（中文 1、拉丁 0.5） |
| `topics.evidence` | 硬 | 「数字与出处」表非空，且实测类数字带作者本人归因 |

用法：

```bash
cd aiv/pipeline
python -m pyv.cli topics check
# 或
make topics
```
