# 视频字幕（口播稿 · 为什么 DDL 同步不能直接把 SQL 文本发过去 · 第三方开发者口径）

> 版本：2026-11-12 首版（EP05，第一季第五期）
> 承接：[《并行接收之后，谁先应用 · 口播稿与字幕》](./字幕-并行apply.md)（EP04）
> 主钩子：**社区讨论的方向不是「把 DDL 当字符串发过去」，而是拆成带语义的结构化对象**
> 选题依据：[`选题库.md`](./选题库.md) 的 EP05（第一季主线「机制族」）

## 一、身份口径（沿用 EP01，硬性约束）

以**独立开发者 / PostgreSQL 社区贡献者**身份讲述公开机制，全程不出现：

- 公司名称、品牌名、产品名、Logo
- 客户名称、案例项目名、内部项目代号
- 未公开的内部数据、内部架构命名、内部人员信息

可出现：

- PostgreSQL、逻辑复制、DDL、WAL、deparser、schema / name mapping 等**公开技术概念**
- 社区邮件、wiki 讨论中已公开的方向
- 作者本人读过的内部设计稿里的**结论性内容**（须标明是设计方案）

> ⚠️ **本期的口径红线（硬要求）**：结构化 DDL **社区讨论里没有一个已经合入主线的最终版本**
> （出处文档原话）。本期讲的是**社区讨论的方向**，不是已发布特性，
> 更不能说「PostgreSQL 18 支持结构化 DDL」。
> 第 10 句必须把这条边界说出来。

## 二、口播稿（10 句，每行一句）

```
大家好，我是关注数据库内核方向的独立开发者。
前面几期都在讲数据怎么复制，这期讲结构怎么跟着走。
最直觉的做法是：DDL 写进 WAL，解码出来原样发给订阅端。
听着最省事，但社区讨论下来，它有 4 条做不到的事。
订阅端只拿到文本，就没法判断这条命令到底做了什么。
所以方向是拆成带语义的结构化对象，分五步走。
先捕获，再结构化，中间过一次 deparse。
deparser 会补全 schema name，也会把没发布的表过滤掉。
最后订阅端按语义执行，这样才支持名字映射和跨版本。
边界要说清：社区还在讨论，还没有合入主线的版本。
```

| 项 | 值 |
| --- | --- |
| 字数 | 260 字 |
| 句数 | 10 句 |
| 实际时长 | 待出片时实测（EP02 为 35.316 秒 / 267 字，本期 260 字） |

> 第 10 句是**边界声明**。EP05 是季末，这期讲的是「怎么判断」而不是「怎么实现」，
> 收在边界上正好把整个季的基调立住。

## 五、数据与机制出处

| 陈述 | 出处 | 状态 |
| --- | --- | --- |
| 直接把 DDL 当字符串发过去的 4 个短板：过滤粒度、名字映射、异构兼容、安全 | `docs/db/logical_decode/逻辑复制支持ddl问题.md` §4.1–§4.4 | **社区讨论**，可引用 |
| 结构化 DDL 的实现可以分成 5 步 | 同上 §2 | **社区讨论**，可引用 |
| deparser 的作用：规范化表示、补全 schema name、过滤未发布对象、拆分混合命令、拒绝不安全表达式 | 同上 §2 第三步 | **社区邮件举例**，可引用 |
| 订阅端按语义 apply 的 5 个动作：读消息头 → 合法性检查 → 名字映射 → 依赖检查 → 重建并执行 | 同上 §2 第五步 | **社区讨论**，可引用 |
| 结构化之后才能做选择性复制、名字映射、语法不兼容修复、异构复制 | 同上 §2 第五步 | **社区讨论**，可引用 |
| 社区讨论里没有一个已经合入主线的最终版本 | 同上 §2 首句 | **原话即红线** |
