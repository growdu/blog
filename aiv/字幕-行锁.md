## 二、口播稿（10 句，每行一句）

```
大家好，我是关注数据库内核方向的独立开发者。
上期讲了订阅端怎么判断两条事务能不能一起做。
回到源头：两个事务改同一行，凭什么不能都改？
MVCC 只管读和写，写和写之间它管不了。
PostgreSQL 在 MVCC 之上加了行锁，一共 4 种模式。
最弱是 KEY SHARE，最强是 EXCLUSIVE，冲突得等。
归纳一下，冲不冲突看一张 4×4 的矩阵。
PostgreSQL 18 源码里，锁藏在元组的 t_infomask 和 xmax 里。
多个事务锁同一行，xmax 装不下，就交给 MultiXact。
这是上游的公开机制，别把它当成谁家的私有扩展。
```

| 项 | 值 |
| --- | --- |
| 字数 | 275 字 |
| 句数 | 10 句 |
| 实际时长 | 实测 35.172 秒 / 275 字 |

> 第 10 句是**边界声明**：明确这是上游 PostgreSQL 的公开机制，
> 避免观众把行锁误当成某家厂商的私有能力，也避免与 EP01~EP05 的
> 「openGauss 额外加的」口径混淆。
> 第 8 句里的「PostgreSQL 18」是**源码版本出处**，不是「18 新增了行锁」。

## 五、数据与机制出处

| 陈述 | 出处 | 状态 |
| --- | --- | --- |
| MVCC 解决读-写冲突，解决不了写-写冲突（lost update） | `docs/database/postgresql-row-lock-deep-dive/index.md` §1.1、§1.2 | 上游公开机制，可引用 |
| 行锁是加在 MVCC 之上的一层写-写协调 | 同上 §1.3 | 上游公开机制，可引用 |
| 行锁共 4 种模式：KeyShare / Share / NoKeyExclusive / Exclusive | 同上 §2.1（`lockoptions.h:14-30`） | 上游公开机制，可引用 |
| KeyShare 最弱、Exclusive 最强，两者冲突 | 同上 §2.4、§3.1 | 上游公开机制，可引用 |
| 4×4 兼容性矩阵的每一格 | 同上 §3.1 兼容性表 | 上游公开机制，可引用 |
| UPDATE 不改 key 列取 NoKeyExclusive，改 key 列或 DELETE 取 Exclusive | 同上 §2.3 | 上游公开机制，可引用 |
| 行锁由 t_infomask 的 4 个 bit + xmax 承载 | 同上 §4.1、§4.3 | 上游公开机制，可引用 |
| xmax 有「删除者」与「仅锁持有者」两种含义（HEAP_LOCK_ONLY） | 同上 §4.3、§4.4 | 上游公开机制，可引用 |
| 多个事务锁同一行时 xmax 装不下，改由 MultiXactId 记录 | 同上 §6.1、§6.2 | 上游公开机制，可引用 |
| 冲突时的 3 种等待策略：Block / Skip / Error | 同上 §3.3 | 上游公开机制，可引用 |
| 画面上的 t_infomask 数值（0x0010 / 0x0040 / 0x0080 / 0x1000） | 同上 §4.1 引的 `htup_details.h` 宏定义 | **源码里的位定义**，不是实测数据 |

> **不得表述为**：行锁是 PostgreSQL 18 新增的能力；行锁是 openGauss 的私有扩展；
> 画面上的矩阵与位值是实测数据。
