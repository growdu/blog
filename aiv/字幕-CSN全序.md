# 视频字幕（口播稿 · CSN 全序 · 第三方开发者口径）

> 版本：2026-11-12 首版（EP02，第一季第二期）
> 承接：[《并行逻辑解码 · 口播稿与字幕》](./字幕-并行解码.md)（EP01）
> 主钩子：**并发提交的时间是乱的，但只要给每次 commit 分配一个单调递增的号，订阅端就能自己排好序**
> 选题依据：[`选题库.md`](./选题库.md) 的 EP02（第一季主线「机制族」）

## 一、身份口径（沿用 EP01，硬性约束）

以**独立开发者 / PostgreSQL 社区贡献者**身份讲述公开机制，全程不出现：

- 公司名称、品牌名、产品名、Logo
- 客户名称、案例项目名、内部项目代号
- 未公开的内部数据、内部架构命名、内部人员信息

可出现：

- PostgreSQL 18、openGauss、reader / worker、逻辑复制、WAL、CSN、commit 顺序等**公开技术概念**
- 上游源码与设计稿中已公开的机制描述

> ⚠️ **本期的口径红线**：CSN 是 **openGauss** 的实现，**不是 PostgreSQL 18 的能力**。
> 口播第 10 句必须把这条边界说出来，不能让观众以为 PG 18 也有 CSN。

## 二、口播稿（10 句，每行一句）

```
大家好，我是关注数据库内核方向的独立开发者。
接着上期的问题：提交顺序到底是怎么定的？
并发时 commit 的先后是乱的，按时间戳排并不可靠。
openGauss 的做法是给每次提交发一个号，叫 CSN。
号从哪来？一个 64 位原子计数器，自增一号就归你。
所以不管谁先谁后，号的顺序永远和领取顺序一致。
这个号会写进 WAL 的提交记录，一路带到订阅端。
订阅端拿到号，就知道这条变更该不该先应用。
整个链路有六层保障，从计数器一直管到订阅端校验。
不过它的边界很清楚：这是 openGauss 的做法，不是 PostgreSQL 18 的能力。
```

| 项 | 值 |
| --- | --- |
| 字数 | 267 字 |
| 句数 | 10 句 |
| 目标时长 | 30~35 秒（EP01 实测 255 字 / 33.156 秒，本期 267 字按同一语速推算约 34.7 秒） |

> 末尾一句是**边界声明**，也是人格规范 §5 要求的「什么时候不该用/不是谁的能力」。
> 这一期结尾落在边界上是有意的：EP01 结尾落在价值上（「实用性很高」），
> 两期一正一反，观众能感觉到这期说的是「一条路，但不是所有人的路」。

## 五、数据与机制出处

| 陈述 | 出处 | 状态 |
| --- | --- | --- |
| 并发时 commit 的先后是乱的 | 同上 §6.2（「即使乱序执行，返回值也是严格递增的」） | 上游公开源码，可引用 |
| 按时间戳排并不可靠 | **通用并发事实**，不是 openGauss 专有结论 | 不标注出处；只作机制背景 |
| `nextCommitSeqNo` 用 `pg_atomic_fetch_add_u64` 分配 CSN | 同上 §二、§6.2（源码行号已记） | 上游公开源码，可引用 |
| CSN 单调性来自原子自增，与 commit 实际时刻无关 | 同上 §6.2 | 上游公开源码，可引用 |
| 全序由六层机制保证 | 同上 §六（L1~L6 表格） | 上游公开源码，可引用 |
| CSN 写进 commit 的 WAL 记录 | 同上 §三、§5.1 | 上游公开源码，可引用 |
| BEGIN 消息携带 CSN（协议新增字段） | 同上 §5.5、§6.5 | 上游公开源码，可引用 |
| 订阅端用 CSN 判断可见性 | 同上 §5.7、§六 L6、§八 | 上游公开源码，可引用 |
| 与 PostgreSQL 18 的 `SerializableSnapshot` 全序是两条不同路线 | 同上 §十一 | 可公开引用 |

> **不得表述为**：PG 18 支持 CSN、CSN 是 PostgreSQL 的能力、
> CSN 比 PG 18 的方案「快 N 倍」（O(1) 与 O(活跃事务数) 是**源码机制对比**，不是实测）。
