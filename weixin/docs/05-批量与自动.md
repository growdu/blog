# 批量回填与自动进草稿

> 核对日期：2026-11-11。接口行为以**真实账号实测**为准。
> 实现见 `weixin/wechat/cli.py`（`batch` / `auto-draft`）、
> `weixin/wechat/publish.py`（`update_draft`）。

---

## 一、结论

**两件事都能做，而且互为支撑：**

| 目标 | 命令 | 做到哪一步 |
| --- | --- | --- |
| 存量文章批量变成草稿 | `wechat.cli batch` | 全部进草稿箱，你按需挑着发表 |
| 新增文档自动变成草稿 | `wechat.cli auto-draft` | 本机定时任务，docs/ 一变就进 |

两者的共同前提是本号**只能到草稿箱**（`freepublish/submit` 实测 48001）。
但这恰恰让「草稿箱」成为一个好用的工作台：**发布决定权回到人手里**，
机器只负责把文章整理成可以直接发出去的状态。

## 二、批量回填：存量 → 草稿箱

```bash
cd weixin && python3 -m wechat.cli batch --dry-run     # 先预检，不调接口
cd weixin && python3 -m wechat.cli batch                # 真跑
```

### 预检口径与实际结果的差别

预检只看**正文原始字数**（便宜的条件），所以它报的数字是**上界**：

```text
$ python3 -m wechat.cli batch --dry-run
预检：将处理 403 篇（不改数据、不调接口）
不合规跳过 105 篇，内容未变跳过 60 篇
```

> 上面是**旧口径**的输出：当时「不合规」的 105 篇是**标题超 32 字**被拦下的，
> 而那个闸门后来被实测推翻（见 [12-标题裁剪与封面.md](12-标题裁剪与封面.md)）。
> 现在标题超长是**裁剪**不是不合规，预检里不再出现这一类。

正文超上限的文章**不再被预检拦下**——它们会在渲染阶段被拆成多篇，
每篇各自成稿。上限默认 60000 字符（可配），拆完草稿箱里是 **736 篇**
而不是 403 篇。

标题超长的文章同样不再被拦下：按内容裁剪到 64 字符后照发。

正文为空的文章（源文件里只剩 front matter）**会被跳过**，理由写进预检输出
和 `out/batch-report.json`——它们做成草稿只是个空壳。以前留下的空壳用
`python3 weixin/tools/prune-empty-drafts.py` 清掉。

拆分规则见 [06-超长文章拆分](06-超长文章拆分.md)。

### 接口配额账

微信的调用上限约 **2000 次/天**。一次全量回填的消耗（实测语料，2026-11-14，
上限 60000 字符）：

| 动作 | 次数 |
| --- | --- |
| 正文图上传（`media/uploadimg`） | 约 120 |
| 封面上传（`material/add_material`） | 736 |
| 建草稿（`draft/add`） | 736 |
| **合计** | **约 900** |

余量约 1100 次，重试的余地比旧口径（上限 20000 时约 1650 次）宽裕得多。
要留出余地时用 `--limit` 分批：

```bash
python3 -m wechat.cli batch --limit 100    # 本轮只处理 100 篇
```

**刷新旧草稿时要多算一次**：带 DDL 代码块的文章（43 篇 / 75 个部分）
`draft/update` 会被 WAF 拦，工具改成 `draft/add` + `draft/delete`，
每次多一次调用。见 [02-接口与发布](02-接口与发布.md#️-draftupdate-会被-waf-拦而-draftadd-不会)。

### 一次跑完要多久

**15 分钟**，几乎全花在 mermaid 上：放行的文章里有 **290 个 mermaid 图**，
每个图要起一次 mermaid-cli（npx + Chrome，约 3 秒）。PNG 按源码哈希缓存在
`weixin/out/mermaid/`，**第二次跑就是秒级**。

### 出错不会连坐

一篇失败不影响其余的：

```text
[1/403] 数据库深入/xxx
  ! 接口报错: /cgi-bin/draft/add failed: [40007] invalid media_id
[2/403] 数据库深入/yyy
  ...
本轮完成: 新建 771 篇，就地更新 0 篇，跳过 0 篇（超限），失败 1 篇
明细:
  ! 某篇标题 (db/xxx/slug) -> /cgi-bin/draft/add failed: [40007] invalid media_id
```

- **拆不开**是「跳过」，不是「失败」：文章放不下就是放不下，跳过并记一笔
- **接口报错**是「失败」：记进明细，退出码 3，其余文章照跑
- 触发 `45009`（调用超上限）会**提前收工**，已建的草稿不会丢，下次接着跑

明细同时写到 `weixin/out/batch-report.json`，长跑之后好回头查。

> 「新建 771 篇」多于「处理 403 篇」——因为 106 篇文章被拆成了多份，
> 每份都是一篇草稿。

## 三、自动进草稿：新增文档

```bash
cd weixin && python3 -m wechat.cli auto-draft
```

它做三件事：

1. **看 `docs/` 变没变**
   - `sync-hexo.py` 要 3 分钟且是全量重建，每两小时白跑一次不是好主意
   - 变了才跑
2. **变了就重新生成 `source/_posts/`**
3. **推进草稿箱**（批量）

### 定时任务只管「新增」，不管存量

launchd 里跑的是 `auto-draft --new-only`：**只处理从没建过草稿的文章**。

| | 谁来跑 | 什么时候 |
| --- | --- | --- |
| 存量回填（几百篇） | **人**手动 `batch` | 一次性的，需要人点头 |
| 新增文档 | **机器** `auto-draft --new-only` | 每两小时 |

分开的理由很实在：存量回填一下子往草稿箱里塞几百篇，还吃掉当天一半的
接口配额——那是需要人点头的动作。而「新增文档自动进草稿」是纯增量，
随时可以做。

> 少了 `--new-only` 的话，定时任务第一次跑就会把整个存量铺进草稿箱，
> 而你可能只是想试水 20 篇。

**改过的文章不自动更新草稿**：`--new-only` 只认「从没建过草稿」的。要更新
某一篇用 `publish <slug>`，要批量更新用 `batch --changed-only`。

### 变更检测看的是「工作区」，不是「提交」

用 `git status --porcelain -- docs` 而不是 `git diff`——**`git diff` 看不见还没
`git add` 的新文件**，而「刚写完还没提交的新文章」恰恰是这个任务存在的理由。

上一次同步到哪个 commit 记在 `weixin/out/.auto-draft-stamp`。判定是两条：

```text
git diff --quiet <上次 commit> HEAD -- docs     # 上次之后提交过的改动
git status --porcelain -- docs                   # 工作区里的改动（含未跟踪）
```

### 触发器：本机 launchd

```bash
cp weixin/deploy/launchd.plist.template \
   ~/Library/LaunchAgents/com.growdu.weixin.auto-draft.plist
# 把模板里的 __REPO__ / __PYTHON__ / __HOME__ 换掉
launchctl load -w ~/Library/LaunchAgents/com.growdu.weixin.auto-draft.plist
```

模板里每两小时一次。**为什么不用 GitHub Actions**：公众号接口要求调用方
出口 IP 在后台白名单里，GitHub 托管 runner 的出口 IP 是动态的，所有调用
都会被 `40164` 挡下——发布动作必须留在固定 IP 的机器上。

**为什么 launchd 而不是 cron**：这台机器是 Mac，会合盖休眠。launchd 的
`StartCalendarInterval` 在错过的时间点醒来后会补跑，cron 不会。

日志：`~/Library/Logs/weixin-auto-draft.log`。

**本机已装好**（2026-11-11）：

```text
~/Library/LaunchAgents/com.growdu.weixin.auto-draft.plist
  → /Users/growduduan/anaconda3/bin/python3 -m wechat.cli auto-draft --new-only
  → WorkingDirectory /Users/growduduan/code/blog/weixin
```

> launchd 的默认 `PATH` 很短，`npx` 找不到，mermaid 就渲染不出来（会降级成
> 源码块）。模板里的 `EnvironmentVariables` 已经把 `/opt/homebrew/bin` 加进
> 去了。

### 第二个定时任务：刷新存量草稿（2026-11-12 加的）

管线版本升到 2（标题按内容裁剪 + 封面卡）之后，草稿箱里已有的那些草稿
就都是旧版做的：标题还是老样子，549 个没有配图的部分还共用同一张默认封面。
`--new-only` 永远碰不到它们（它们有草稿），所以另开了一个任务：

```text
~/Library/LaunchAgents/com.growdu.weixin.refresh-drafts.plist
  → python3 -m wechat.cli batch --limit 100
  → 每 6 小时一次（0:30 / 6:30 / 12:30 / 18:30）
  → 日志 ~/Library/Logs/weixin-refresh-drafts.log
```

一轮约 100 篇、约 360 次调用，四轮一天约 1450 次，留在每日 2000 次配额之内。
**这是一次性的活**：跑完（约 553 篇）就可以把它 unload 掉。

#### 实测：一轮就吃光配额（2026-11-13）

上面那个「360 次/轮」是按**文章**估的，漏了**部分**。一篇拆成 6 篇的文章
要发 6 个草稿，每个草稿都要传封面 + 建草稿（+ 正文图）。实测：

| 时刻 | 这一轮做了什么 | 结果 |
| --- | --- | --- |
| 00:30 | 新建 110 篇 + 就地更新 522 篇 = **632 个草稿** | 撞上 `45009`，配额用尽 |
| 06:30 | 新建 1 篇 + 就地更新 7 篇 = **8 个草稿** | 又撞上 `45009`（配额按自然日算，00:30 已经用完） |

所以**一轮 100 篇 ≈ 1450 次调用 ≈ 一整天的配额**。定时任务虽然每 6 小时
跑一次，实际能推进的只有每天的第一轮。

两件事因此变得值钱：

1. **封面素材缓存**（见 [02-接口与发布](02-接口与发布.md#十封面素材同一个封面只传一次)）：
   一轮少传约 300 个封面，约省 15%。
2. **`--limit` 要按「调用数」算，不是按「篇数」算**：拆成多篇的文章一篇
   就顶好几篇。限额调小会拖慢刷新，调大则一轮就撞墙。

### 刷完要多久

存量 1453 个草稿，按每天一轮约 630 个草稿算，**还要两三天**。配额按自然日
0 点重置，所以实际节奏是「每天 00:30 那一轮」。

### 别让两个批量同时跑

批量任务之间有一把锁（`out/batch.lock`，存的是进程 pid）。
锁在时另一个批量会打印「另一个批量任务正在运行，本次跳过」然后退出，
不会建出第二份草稿。进程没了说明是崩溃留下的，下一次直接接管。

账本 `out/state.json` 的写入也加了文件锁：它是整个读出来、整个写回去的，
两个写者同时动就会互相覆盖，而少掉的那条记录对应的草稿其实已经在草稿箱里，
下一次跑会再建一份——正是三层幂等要防的那件事。

### 通知

`auto-draft` 跑完会推**一条汇总**通知（不是每篇一条）：

```text
公众号草稿已就绪
本轮新建 3 篇，就地更新 1 篇，跳过 0 篇（超限），失败 0 篇

去公众号后台点「发表」即可发布：https://mp.weixin.qq.com/...
```

## 四、幂等：为什么重跑是免费的

这是批量与定时两条链路的共同基础。三层：

| 层 | 键 | 防的是什么 |
| --- | --- | --- |
| 内容层 | `sha256(正文 + 分类标签)` | 正文没变就不重建草稿 |
| 草稿层 | `media_id` | 已有草稿不重复 `draft/add` |
| 发布层 | `publish_id` + `publish_status` | 已在发布中就不重复 `submit` |

**关键在于「内容没变」是在上传任何一张图之前判定的。** 第二遍跑全语料，
接口调用数是 **0**——不是「少一点」，是零：

```text
$ python3 -m wechat.cli batch      # 第一遍
$ python3 -m wechat.cli batch      # 第二遍
没有需要处理的文章（不合规 118 篇，内容未变 357 篇）
```

指纹覆盖**分类标签**而不只是 markdown：标签是正文的一部分，标签一改就必须
重建草稿，否则改动永远到不了读者那里。

### 草稿是就地更新的，不是新建的

文章改了以后，工具调的是 `draft/update` 而不是 `draft/add`：

```text
POST /cgi-bin/draft/update
{"media_id": "...", "index": 0, "articles": {...}}
```

`draft/add` **总是新建一篇**。用它的话，改一次文章草稿箱里就多一份旧版本，
读者会看到同一篇文章的两个版本。实测 `draft/update` 在本号可用（errcode 0，
草稿总数不增）。

> `update` 的 `articles` 是**一个对象**，不是 `add` 里的数组；`index` 是它在
> 多图文草稿里的位置。

### 账本和草稿箱会对不上

`out/state.json` 是这套工具唯一的幂等依据。但它在**微信后台**这一侧没有对手：
人可以在后台把一篇草稿删掉，账本不知道，于是那篇文章**永远不会再进草稿箱**——
`batch --new-only` 认定「建过了」，`batch` 认定「内容没变」，两条路都跳过，
而且不报任何错。

实测就踩到过：账本 10 条，草稿箱只有 9 篇，`dpdk/vpp与dpdk的关系` 那条
`media_id` 已经是 `40007 invalid media_id`。

`reconcile` 就是补这个洞：

```text
$ python3 -m wechat.cli reconcile --dry-run
预检：草稿箱 9 篇，账本 10 条，将清理 1 条（不写盘）
  - 草稿已不存在: dpdk/vpp与dpdk的关系 (08QUqqaDBm_vIgdclIU8XHc1...)

$ python3 -m wechat.cli reconcile
草稿箱 9 篇，账本 10 条，已清理 1 条
```

清理的动作是**只清掉草稿那一半**（`media_id` 与 `fingerprint`），`publish_id`
保留——文章发过就是发过，跟草稿被不被删无关。清完之后 `batch --new-only`
会把它当成新文章重新推进草稿箱。

两个安全阀：

| 情况 | 行为 |
| --- | --- |
| 草稿箱空、账本非空 | **拒绝清理**（退出码 2）。这更像账号或凭据不对，不是草稿真的被删光了；照清的话整个账本会被扔掉，下次批量把所有草稿重建一遍。确实要清加 `--force` |
| 草稿箱里有账本没记的草稿 | 只报告，不动账本。通常意味着账本被删了——那种情况下下次批量会给每篇文章建第二份草稿 |

对账走 `draft/batchget` 分页拉整个草稿箱（`no_content=1`，只回标题不回正文），
一次调用能看清几十上百篇，不是每条账本打一次接口。

## 五、与 `publish/spec` 契约五的关系

仓库里另一条线（`publish/spec/00-架构设计.md`、`publish/spec/06-发布计划与调度.md`）
在设计**跨平台**的发布调度。它和本模块的分工是清楚的：

| | 契约五 | 本模块 |
| --- | --- | --- |
| 范围 | 公众号 / YouTube / B站 / 头条号 / 视频号 | **只有公众号** |
| 选内容 | `platforms` 非空的内容单元，按 `publish_on` 排，每周一篇 | 全部合格的文章，按分类/显式指定 |
| 触发 | 周五一次（周键幂等） | 定时任务 + 变更检测 |
| 终点 | manifest → 各平台 adapter → `publish/outbox/` | 公众号草稿箱 |

**契约五明确说它对 `weixin/` 只读**，并且
「`wechat.cli publish` 是公众号 adapter 的入口，`publishkit.cli publish` 是
跨平台调度入口，两者并存不冲突」。

有一处需要留意：**契约五的「每周一篇」和本模块的「全部进草稿箱」在公众号这条
线上是重叠的。** 契约五选出的那篇文章，本模块也会把它推进草稿箱——只不过
契约五走的是跨平台调度层，幂等键在 `publish/outbox/`，本模块的幂等键在
`weixin/out/state.json`。两者是**同一篇内容的两份状态记录**，不是两次发布：
草稿箱里只会有一篇（内容层指纹相同 → 复用同一个 `media_id`）。

如果将来要合并这两条线，正确的做法是让契约五的 adapter 调用
`wechat.cli publish`（单篇），而不是让 `batch` 参与跨平台调度。

## 六、边界与风险

| 事项 | 结论 |
| --- | --- |
| **平台上的合集/分类归属** | 仍然要人工，接口层面做不出来，见 [04-分类与合集.md](04-分类与合集.md) |
| **发表** | 本号 `freepublish/submit` 是 48001，最后点「发表」由人完成 |
| **`out/state.json` 被删** | **所有文章的草稿会被重新建一遍**，草稿箱里会多出 357 篇重复内容。清理 `out/` 之前先留着它：`git clean -xdf -e weixin/out/state.json` |
| **每日配额** | 约 2000 次；一次全量回填约 1009 次，留一半余量给重试 |
| **mermaid 首次渲染** | 290 个图约 15 分钟；PNG 按源码哈希缓存，第二次跑秒级 |
| **代理环境** | 出口 IP 以微信 `40164` 报错里的为准，见 [02-接口与发布.md](02-接口与发布.md) |
| **多机并发** | 幂等键在 `out/state.json` 里，两台机器各有一份就会各建一份草稿。别让两个定时任务同时跑 |
