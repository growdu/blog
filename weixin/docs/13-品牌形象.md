# 品牌形象：把作者写好的东西放到读者看得见的位置

> 本文是 `weixin/wechat/brand.py` 与 `weixin/wechat/digest.py` 的规格说明。
>
> 数据可用 `python3 weixin/tools/measure-brand.py` 复跑（纯本地，不调接口）。

---

## 一、为什么要做这一轮

草稿箱是读者认识 growdu 的地方。改造之前，569 篇文章、1432 个渲染部分
被量化过一遍，结论是：**品牌素材一直在语料里，只是没有被放到读者看得见
的位置。**

| 指标 | 改造前 | 说明 |
| --- | --- | --- |
| 结尾有作者落款 | 15 / 1432（**1%**） | 读完一篇，没有「这是 growdu 写的」的落点 |
| 正文带作者自述块 | 82 / 569（14%） | 品牌素材只出现在 14% 的文章里 |
| **开头有作者自述引用块** | **226 / 569（40%）** | 系列定位、立场、源码版本 —— 品牌金矿未被使用 |
| 摘要带判断/结论词 | 35 / 569（6%） | 94% 是话题句，门面层没传递「判断」 |
| 摘要为空 | 75 / 569（13%） | 图片行被当正文，拼完被 strip 成空串 |
| 摘要疑似漏图注/过短 | 48 / 569（8%） | 「@AI产出图」「AI 绘画作品」「版本：V1.0」 |
| 开头是「分类 + 全文共N部分」 | 1058 / 1432（74%） | 第一屏是机器记账 |

素材长什么样：

- `database/postgresql-catalog-storage` 开头的三列表，就是一篇标题页：

  | 编写人 | 编写内容 | 编写时间 |
  | --- | --- | --- |
  | growdu | 初稿，面向 PostgreSQL 内核开发 / DBA / 内核爱好者，把"一张表的元数据到底存在哪里、谁去加载它、加载到内存之后长什么样…"完整拆开。配套源码版本：PostgreSQL 18 dev（~/cwork/postgresql，REL_18_3 之后 77 commit）。 | 2026-09-29 |

- `ai/02_AI到底聪明在哪…` 开头的一句：「这是「AI是怎么回事」系列的第 1 篇。
  我一直很好奇 AI 到底是怎么工作的，于是花了很长时间去拆这个东西…」

- `life/shehui/economic-downturn-deep-dive` 的第一段：「写经济分析不是我的
  专业。写内核才是。」

### 一条原则

**不替作者写定位，把他已有的定位挖出来用。**

工具不发明文案。作者写好的定位被搬到读者看得见的位置；作者没写的不编。
理由有二：一是编出来的定位一旦和文章对不上，反而毁掉信任；二是从自己
的文字里长出来的定位，和写作是一体的，改文案不会让它失真。

## 二、四项改动

### 2.1 名片卡（`brand.byline_html`）

正文开头三列表「编写人 / 编写内容 / 编写时间」在渲染时被提出来，变成文章
头部的卡片：

```html
<section style="margin:0 0 18px;padding:12px 14px;border-left:3px solid #3d7ea6;background:#f6f8fa;">
  <p style="...">growdu ｜ 2026-09-29</p>
  <p style="...">面向 PostgreSQL 内核开发 / DBA / 内核爱好者，把"一张表的元数据到底存在哪里…"完整拆开。配套源码版本：PostgreSQL 18 dev（~/cwork/postgresql，REL_18_3 之后 77 commit）。</p>
</section>
```

规则：

| 规则 | 为什么 |
| --- | --- |
| 按**表头名**找列，不依赖列序 | 表可以换形状；列序一变就取错列 |
| 卡片**只出现在第 1 部分** | 它是文章的标题页，后面的部分是正文续篇 |
| 表本身从正文流里移除 | 一张三列表、每格一个段落的表，是读者要滑过去的东西，不是标题页 |
| 「初稿，」这类写作状态标记摘掉 | 它是写作的状态，不是文章的描述；卡片开头写「初稿，」像没写完 |
| 描述超过 180 字按句号裁 | 卡片写成五段就又是段落了 |
| 引用出处（`来源：`/`译自`/`原文`）与免责声明不算自述 | 那是引文，不是定位 |
| 全部 inline style，**0 个 `class`** | 公众号只认写在元素上的 style |

卡片覆盖：**138 / 569 篇（24.3%）**。

### 2.2 落款（`brand.signature_html`）

每一部分末尾一行：

> 本文作者：growdu ｜ 完整版、勘误与后续更新见文末「阅读原文」

覆盖率 **1% → 100%**（1432 个渲染部分全都有）。署名跟着 `--author` 走，
所以 `--author "growdu｜内核开发者"` 会同时改到微信 byline 和落款。

落款放在**参考链接之后**：参考链接是文章的结尾，落款是读完之后看到的
最后一行。

### 2.3 摘要取材（`digest.article_digest`）

摘要按「作者自己写过、且信息量最大」的顺序取材：

| 级别 | 来源 | 命中 |
| --- | --- | --- |
| 1 | 标题页的「编写内容」 | 74 篇 |
| 2 | 开头的自述引用块（「这是一篇程序员视角的反思…」） | 129 篇 |
| 3 | 结论类小节（总结/结论/小结/结语/要点/写在最后）的段落 | 约 30 篇 |
| 4 | 正文第一段（兜底） | 其余 |

各级都有守卫，宁可退回下一级也不取坏材料：

| 守卫 | 拦掉什么 |
| --- | --- |
| 描述 ≥ 20 字 | 「初稿」 |
| 描述不能只讲方法（`结合 X 源码`） | 方法适合放名片，不适合当摘要 |
| 开头块不能是元数据（`配套源码：`/`文档版本：`） | 同上 |
| 结论段 ≥ 20 字 | 「选择 haproxy 来实现。」是答案不是摘要 |
| 结论段必须是完整句子 | 「[1]: https://…」是参考不是结论 |
| 结论段不能是引导句（以「：」结尾） | 「当前市场已经进入：」 |
| 图片行整行跳过 | 摘要变成「@AI产出图」 |
| 首段不足 30 字才补第二段，且**只在开头小节内**补 | 摘要变成 6 个字；或把开头和结尾拼在一起 |

实测（全语料 569 篇）：

| 指标 | 改造前 | 改造后 |
| --- | --- | --- |
| 摘要为空 | 59 | 59（不倒退） |
| 摘要过短（< 25 字） | 184 | **115**（少 38%） |
| 摘要被改写 | —— | 254 篇（44.6%） |

改写样例：

| 文章 | 改前 | 改后 |
| --- | --- | --- |
| `database/pgaudit-deep-dive` | 合规要求下，PG 必须能回答 3 个问题：谁在什么时间做了什么… | 把 pgAudit 从 1.0 起，到 session / object / csvlog 三种模式、log_line_prefix / log_statement 集成、SOX / HIPAA… 完整拆开。 |
| `db/postgresql/learning-path/09-wal-and-recovery` | 每个数据页面的修改，必须在写盘前先写 WAL。原因： | 目标：吃透 PG 的 Write-Ahead Logging 子系统——XLogRecord 结构、rmgr 注册表、redo/undo、checkpoint、recovery、流复制。 |
| `life/shehui/self-host` | TL; ← **真 bug**：TL;DR 的半角分号被当成句号 | TL;DR：原文作者的方案是「17 个原生 systemd 服务 + 11 个 Podman 容器，跑在一台 180~359 欧元的 N100 迷你主机上…」 |
| `life/gaokao/biology-methods` | 第三行和第六行是这一篇的核心： | 面向中等水平（60~75 分）的考生，目标是稳定到 85 分以上。生物和物理、化学都不一样：它是省命题、它是赋分科目… |

第 1 部分用整篇的摘要，后面的部分各说各的（`digest.part_digest`），
草稿箱里不会有一排一模一样的摘要。

摘要不再重复标题：只有**标题被裁剪过**时才把原标题带进摘要；分篇编号
的情况标题行里已经有了，不重复。

### 2.4 分篇措辞

| 改前 | 改后 |
| --- | --- |
| 全文共 5 部分，这是第 2 部分。 | 本文共 5 部分，这是第 2 部分。 |
| 接上文《标题（一）》。全文共 5 部分，这是第 2 部分。 | 接《标题（一）》。本文共 5 部分，这是第 2 部分。 |

「全文共 N 部分」读起来像整个站点的规模；「接上文」是印刷书的语气，
这里是信息流。

## 三、连带的技术改动

| 改动 | 为什么必须有 |
| --- | --- |
| `split.framing_reserve(title, tag, extra)` 增加 `extra` 参数 | 名片卡与落款要占正文的字符。预留量算少几十个字符，不会让文章短一点，只会让整篇发不出去 |
| `room_for` 按部分精确计算 framing | 第 1 部分有卡片，第 2 部分没有 |
| `PIPELINE_VERSION` 2 → 3 | 正文变了但 markdown 没变，内容哈希不变；不升版本的话 1121 篇存量草稿会被原样复用，永远刷不出品牌元素 |
| `cli._branding` 统一产出卡片/落款/摘要 | `convert` 预览与草稿走同一条路，两者不会两样 |
| `mdparse.inline_text` / `mdparse.block_text` | 把块 AST 还原成纯文本，取材要用 |

## 四、边界

- **不自动发表。** 账号是订阅号个人主体未认证，`freepublish/submit` 返回
  48001；这一轮只把草稿做好，发表仍然是人工点一下。
- **不替作者写定位。** 素材只从文章里挖。
- **存量草稿要靠定时任务刷新。** `PIPELINE_VERSION` 升到 3 之后，
  `com.growdu.weixin.refresh-drafts`（每 6 小时，`batch --limit 100`）会把
  存量草稿逐篇刷新到新版本，配额用完就等第二天。
- **公众号昵称拿不到。** `/cgi-bin/account/getaccountbasicinfo` 对该未认证
  账号返回空昵称（`errcode: 0` 但 `nick_name` 为空），`getaccountprofileinfo`
  返回 40066。**本号昵称是 `growdu`**（2026-11-13 由账号所有者确认）——
  接口取不到，只能人工写进文档。
- **`author` 已经进了内容指纹**（2026-11-14 补上）。以前指纹只算 markdown 正文、
  标题、分类标签，单独改 `--author` 不会让已有草稿重刷：草稿会被判为
  「内容未变」而原样复用，署名还是老的。现在署名和分类标签同理——它也是
  存进微信的那个字段，改了就一定刷得到。
  **只有署名与默认值不同时才计入指纹**：草稿箱里那批就是用默认署名建的，
  无条件算进去会让 455 篇全部重发一遍，而正文一个字都没变。跟标题裁剪
  那一条是同一个道理。
