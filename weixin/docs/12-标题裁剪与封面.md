# 标题裁剪与封面卡

> 2026-11-12 新增。本文档记录两件事：**标题的真实上限到底是多少**，
> 以及**没有配图的文章怎么才能不像一篇**。
>
> 实现见 `weixin/wechat/titles.py`、`weixin/wechat/cover.py`，
> 接入点见 `weixin/wechat/cli.py` 的 `_effective_title` / `_upload_cover` / `_cover_card`。

---

## 一、标题上限：实测推翻了两版结论

这个数字在项目里错了两次，都写进了文档：

| 版本 | 结论 | 来历 |
| --- | --- | --- |
| 初版 | 64 字符 | 二手资料，抄的是**编辑器 UI** 的输入框上限 |
| 试点时 | 32 字符 | 官方 `draft/add` 字段表写着「不超过 32 个字」，当时照抄 |
| **实测** | **API 85 字符 / 编辑器 64 字符** | 见下 |

### 实测过程

用真实账号直接打 `draft/add`，只改标题长度，其余字段不变：

| 标题长度 | 结果 |
| --- | --- |
| 85 | ✅ 建草稿成功，回读标题与提交完全一致 |
| 86 | ❌ `[45003] title size out of limit` |
| 120 / 300 / 600 / 1000 | ❌ 同样 `[45003]` |

二分定位到的边界就是 **85**。这个值和字段表上的 32 对不上，
但接口的实际行为是 85——**字段表过时了**。

顺带一个反证：现有草稿箱里有一批 **33～35 字符**的标题（比如
「PostgreSQL 逻辑复制里 `RUNNING_XACTS` 写入机制与快照 `xmin / xmax / xip` 的演化：源码级深度拆解」拆出来的各部分），
全部建草稿成功。**32 这道闸门拦下的 105 篇文章，从头到尾都是冤枉的。**

### 为什么最后取 64

两个上限各有各的约束：

- **API 层 85**：`draft/add` 能收。
- **编辑器层 64**：后台编辑器的标题输入框最多让打 64 个字（含标点）。
  这条来自多个 web 来源，**未能在后台 UI 里直接验证**（要登录），
  但它和「32 字」的流传路径是同一批二手资料，且方向更保守。

「发表」这一步在这个账号上必须由人点（`freepublish/submit` 返回 48001，无权限）。
所以工具的产物必须是**人点一下就能发出去的**——**取更严的 64**。

> 代码位置：`wechat/titles.py` 的 `TITLE_LIMIT = 64`。

### 留下的影响

`TITLE_LIMIT` 从「拒绝条件」变成了「**裁剪条件**」：

- 以前：标题超长 → 整篇跳过，记进报告，文章永远发不出去。
- 现在：标题超长 → **按内容裁剪**，原文进摘要，文章照发。

## 二、裁剪规则：按内容切，不是按长度截

「截断到 64 个字符」是最省事也最难看的做法：会把单词砍成半个，
把句子砍成半句，读者在标题里读不出这篇文章讲什么。

这个语料的标题几乎都是「**主标题：副标题**」的写法——冒号就是天然的切点。
所以裁剪按切点阶梯来：

| 级别 | 切在哪 | 说明 |
| --- | --- | --- |
| 1 | `：` `:` `——` `—` `---` ` - ` | **强分隔符**，主标题与副标题的边界，优先 |
| 2 | 空格 `｜` `\|` `·` `（` `、` `，` `；` `/` | **弱分隔符**：强分隔不成立时，取**所有弱分隔符里最长的、且放得下的**那个头部 |
| 3 | 直接硬切 + `…` | 完全没有边界时才走这条，并**明确标记被截断** |

几条细则：

- **切出来的头部至少 6 个字符**（`_MIN_HEAD`），太短就不算一个标题。
- **括号要配平**：切在括号中间会留下落单的 `（`/`）`/`【`/`】`，先配平再去掉尾部标点。
- **`https://` 里的冒号不算切点**：`https` 结尾的头部不作为候选。
- **markdown 链接拍平成文字**：微信标题是纯文本，`[kali](https://…)搭建docker`
  应该是「kali搭建docker」，不是把整条链接显示出来。
- **给拆分的编号留位**：拆分出的部分是「标题（一）」「标题（二）」，
  共享的标题要留 3 个字符（`SUFFIX_RESERVE`），否则最后一部分会超限 1 个字符。

其中第 8 篇是「主标题本身也超长」的情况：冒号前的内容就已经 60 个字符，
放得下就不切，放不下就退到弱分隔符（这里的空格），取最长的那个头部。

### 原标题不丢

裁剪后的标题会进摘要，格式是「**原标题｜摘要**」，截到 120 字以内。
读者在公众号里看到的是裁剪后的标题，但摘要里留着完整的原题，
搜文章的人还能搜到。

### 一致性：所有地方都用同一个标题

裁剪后的标题会出现在**标题、过渡语、封面卡、摘要**四处。
这四处必须一致，否则会出现「正文里说第（三）部分，封面写着第（八）部分」这种错位。

所以流水线里只有一个入口：

```python
def _effective_title(post) -> str:
    return effective_title(post.title)   # = titles.effective_title
```

**指纹也同时纳入原标题和裁剪后标题**（`_fingerprint`），
这样「裁剪规则改了」也能让草稿被识别为需要更新，而不是永远停在旧版本。

## 三、封面卡：549 篇共用一张图的解法

### 问题

上一轮回填完成后，草稿箱 766 篇、渲染出的部分 765 个，
其中 **409 个带衔接语、119 个带参考链接区块**，
而**一张图都没有的部分有 549 个（71.8%）**。

没有图的草稿只能共用仓库自带的那张默认封面。
于是草稿箱里出现了**几百篇长得一模一样的文章**——
在公众号后台的列表里，它们是一排没有辨识度的缩略图。

### 方案：本地画一张封面卡

不引新依赖（`pillow` 本来就在），用 Pillow 画 **900×383**（2.35:1，
公众号封面列表的比例）：

- **底色**：竖向渐变，色相由 slug 的 sha1 决定，取品牌蓝紫区间（195°～250°），
  所以每篇不同、但整体像一套。
- **左侧色条**：强调色。
- **分类**：小字，浅灰。
- **主题**：大字，最多 2 行。取的是标题**第一个分隔符之前**的部分
  （`titles.topic`）——也就是「这篇文章讲什么」，而不是把完整标题再抄一遍。
  拆分的部分还会带上编号，比如「PostgreSQL Background Worker 全解（八）」。
- **右下角**：`growdu.cn`。

缓存：文件名是 `sha1(slug|title|category|text)[:12].png`，落在 `weixin/out/covers/`。
标题或分类变了才会重画。

### 取用链扩到 5 级

```
1. 命令行指定的封面（--cover / WX_COVER）
2. 文章的首张本地图
3. 文章的首张外链图
4. 本地生成的封面卡          ← 新增
5. 仓库自带的默认封面
```

- **有图的文章不受影响**：仍然用自己的首图。封面卡只救「一张图都没有」的部分。
- **画不出来就回落第 5 级**：机器上没有任何中文字体时，封面卡画不了，
  这时回落到默认封面并打印一行提示——**绝不因为画不出封面卡而丢掉一篇文章**。

### 字体

按顺序找，找不到就退：

```
/System/Library/Fonts/Hiragino Sans GB.ttc
/System/Library/Fonts/Supplemental/Songti.ttc
/System/Library/Fonts/STHeiti Medium.ttc
/Library/Fonts/Arial Unicode.ttf
/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc
/usr/share/fonts/truetype/wqy/wqy-zenhei.ttc
```

前四个在 macOS 上都已验证可加载。Linux 上走 Noto / 文泉驿。

### 效果

`ai/20_外网与AI工具使用指南` 拆成 10 部分，生成了 10 张封面卡，
每张带不同的色相、不同的编号。草稿箱里这 10 篇不再共用一张图。

## 四、相关的数字变化

`python3 -m wechat.cli audit`（2026-11-12）：

```text
语料: 568 篇, 33 个分类

闸门（逐层收紧，每层只数上一层放行的文章）:
  标题 <= 64 字符         放行  568  需要裁剪   18   ← 超长不再拦下，改裁剪
  原始正文 <= 20000 字       放行  495  超长   73   ← 超长不再拦下，改拆分
  渲染后 <= 20000 字符       单篇放得下  373  需要拆  122

可发布: 568 篇 (100.0%)，草稿总数 1490 篇
  其中需要拆成多篇: 197 篇
  其中拆不开（单块就超限）: 0 篇
  其中只有关掉代码高亮才放得下: 24 篇
```

标题那一层从「拦下 105 篇」变成「**放行 568 篇，其中 18 篇需要裁剪**」。
**可发布率从 81.5% 变成 100%。**

> 1490 是**估算**（按「无 mermaid 渲染器」算，图按源码算），
> 真实流水线里图只是一张 PNG，实际草稿数会略少。
> 上一轮的实跑是估算 784 / 实跑 766，差 18 篇。
