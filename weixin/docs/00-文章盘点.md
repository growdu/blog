## 三、mermaid：最大的成本项

| 指标 | 数值 |
| --- | --- |
| 含 mermaid 的文章 | 148 篇 |
| mermaid 图块总数 | 1280 个 |
| **解析失败率** | **8.2%**（102/1239，见 `tools/mermaid-audit.md`） |

站点用客户端 JS 渲染 mermaid，公众号没有 JS，所以每个图块都要预渲染成 PNG。
**失败率 8.2% 意味着失败路径是常规路径，不是边缘情况**——所以渲染失败必须
显式降级成源码块并标注，绝不能静默丢图。

失败的主要根因（`tools/mermaid-audit.md` 已列全）：

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| `A[文字]::: class` | mermaid v10 的类名与 `:::` 之间不允许空格 | `A[文字]:::class` |
| `A[文字 (含括号)]` | 标签里的 `(` `)` `:` `;` `,` `"` 需要引号 | `A["文字 (含括号)"]` |
| `--> [多词标签]` | 箭头后直接跟匿名节点 | 给它一个 ID |
| `mindmap` 节点含标点 | mindmap 语法比 flowchart 严格 | 改缩进层级，去掉标点 |

## 四、合规分析

三层闸门，每一层拦掉不同的文章：

### 第一层：标题 ≤ 32 字（官方字段表）

| 结果 | 篇数 | 占比 |
| --- | --- | --- |
| ≤ 32 字 ✅ | 459 | 81.4% |
| > 32 字 ❌ | 105 | 18.6% |

标题长度中位 14、最长 85。超限的 105 篇集中在**长技术标题**：
「PostgreSQL 逻辑复制 streaming 与 spill：从 reorderbuffer 到 `<subid>` 完整解析」
这种写法在博客里没问题，在公众号里放不下。

> **这是一个内容决策，不是工具能自动解决的**：要么把标题改短（去掉副标题、
> 去掉冒号后的补充说明），要么放弃推这类文章。工具只负责**提前拦下来并列出清单**。

### 第二层：原始正文字数 ≤ 20000

| 区间 | 篇数 |
| --- | --- |
| < 2000 | 225 |
| 2000 – 5000 | 111 |
| 5000 – 10000 | 75 |
| 10000 – 20000 | 80 |
| **> 20000** | **73（12.9%）** |

### 第三层：渲染后 content ≤ 20000 字符（**权威闸门**）

官方限制的是 **HTML 源码字符数**，标签和样式都算进去，所以这一层才是准的。

| 版本 | 正文中位 | 超限 |
| --- | --- | --- |
| 带代码高亮 | 10970 字符 | 215 篇（38.1%） |
| 关闭代码高亮 | 8631 字符 | 191 篇（33.9%） |

**原始字数是必要条件，不是充分条件**：全语料有 38 篇过了原始字数预检，
渲染后仍然超限。所以 publish 路径必须在渲染之后**再卡一次**。

### 最终结果

| 结果 | 篇数 | 占比 |
| --- | --- | --- |
| **可发布** | **357** | **63.3%** |
| 标题超限 | 105 | 18.6% |
| 渲染后超 2 万字符 | 87 | 15.4% |
| 原始正文超 2 万字 | 73 | 12.9% |

（三类原因有重叠，所以合计超过 207。）

## 五、超限文章的本质问题

38% 的文章渲染后超限，**省不下来的部分**：

| 部分 | 占 HTML 体积 | 能省吗 |
| --- | --- | --- |
| `<span>`（代码高亮） | 24.4% | 能——超限时自动关闭高亮 |
| `<p>` | 10.0% | 部分——样式串已压到最短 |
| `<code>`（行内代码） | 9.9% | 部分 |
| `<td>` | 7.8% | **难**——一个 20×5 的表格光单元格样式就 4400 字符 |
| `<pre>` | 3.2% | 难 |

**结论：这是平台的结构性约束，不是实现缺陷。** 20000 字符的 HTML 里，
放不下一篇带大量表格和代码的源码级深潜文章。出路只有两条：

1. **拆成多篇**（连载）——会破坏「一次讲透」的叙事结构，是内容决策
2. **公众号发摘要版，全文放在「阅读原文」**——推荐，成本最低

工具不替人做这个决定，但会**明确报出哪一篇超了多少**，让人知道该选哪条路。

## 六、一个反直觉的结论

**越长的文章越难发到公众号。** 这和「内容质量决定传播」的直觉相反：

| 文章类型 | 可发布性 |
| --- | --- |
| 500 字的概念科普 | 轻松（一篇几百字符的 HTML） |
| 3000 字的实践记录 | 没问题 |
| 8000 字带 10 个代码块的技术文 | 紧张 |
| 6000 字带 28 个代码块 + 41 行表格的源码级深潜 | **放不下**（渲染后 9 万字符） |

所以公众号这条线的选题，和博客不一样：**博客适合写深，公众号适合写透**。
一个能同时服务两边的形态是「**公众号发 3000 字的核心结论 + 阅读原文指向
8000 字的完整推导**」——这也是前作《运营手册》说的「网站是母版，其他是切片」。

## 七、复算命令

```bash
cd /Users/growduduan/code/blog

# 文章清单与合规状态
cd weixin && python3 -m wechat.cli scan

# 全量统计（本文所有数字的来源）
cd /Users/growduduan/code/blog && python3 - <<'PY'
import sys, re, pathlib, statistics, collections
sys.path.insert(0, 'weixin')
from wechat.posts import discover, check_eligibility
from wechat.mdparse import parse
from wechat.render import render

posts = discover(pathlib.Path('source/_posts'))
print('文章数:', len(posts))

titles = [len(p.title) for p in posts]
print('标题 <=32:', sum(1 for n in titles if n <= 32))

raws = [len(re.sub(r'\s', '', p.body)) for p in posts]
print('原始正文超 20000 字:', sum(1 for n in raws if n > 20000))

hi, lo = [], []
for p in posts:
    blocks = parse(p.body)
    hi.append(render(blocks).content_length)
    lo.append(render(blocks, highlight=False).content_length)

print('渲染后超 20000 字符（高亮）:', sum(1 for x in hi if x > 20000))
print('渲染后超 20000 字符（无高亮）:', sum(1 for x in lo if x > 20000))

final = sum(1 for p, h, l in zip(posts, hi, lo)
            if check_eligibility(p).ok and min(h, l) <= 20000)
print('最终可发布:', final)
PY
```
