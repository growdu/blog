# 超长文章拆分

> 正文上限**不是平台的硬限制**，是这篇工具的一个选择——所以它能配。
> `draft/add` 实测收下 10 万字符的原样正文，一个字都没少；官方字段表里
> 那句「content 少于 2 万字符」，和同一张表里的「标题 32 字」一样，是旧
> 版本的抄本。后台编辑器那边也确认过不截断（2026-11-14，账号所有者打开
> 一篇长草稿看过，正文完整）。默认上限取 **60000 字符**
> （`--max-length` / `WX_MAX_LENGTH` 可改），读者看到的是约 1.5 万字，
> 而不是以前的 5000 字。

## 一、结论

| 问题 | 答案 |
| --- | --- |
| 上限是多少 | 默认 **60000 字符**（渲染后的 HTML）。`--max-length` / `WX_MAX_LENGTH` 可改（实测天花板 100000）；**上限进了内容指纹**，改了就会重刷 |
| 什么时候拆 | 渲染后正文 > 上限（先试关高亮，再拆） |
| 拆在哪 | 标题边界优先，其次段落，最后表格行 / 代码行 |
| 每部分叫什么 | `原标题（一）`、`原标题（二）`…… |
| 怎么衔接 | 开头一句说明这是第几部分、接哪一篇；结尾一句指向下一篇 |
| 链接怎么办 | 每部分末尾带**这一部分用到的**链接 |
| 拆不开怎么办 | 先按实测溢出量**再切一次**，仍然拆不开才跳过并记下原因，**不截断** |
| 账本怎么记 | 第一部分记 `slug`，其余记 `slug#2`、`slug#3`…… |

## 二、为什么是渲染后长度

限的是渲染后的 HTML 源码字符数，而 HTML 源码比 markdown 大得多：
每个段落、每个单元格、每个高亮 token 都带着自己的 style。

实测（569 篇全语料）：

| 口径 | 放得下 |
| --- | --- |
| 原始正文 <= 60000 字 | 563 篇 |
| 渲染后放得下（带代码高亮） | 465 篇 |
| 渲染后放得下（关掉高亮） | 483 篇 |

所以「原始正文多长」根本不是判据。工具以前拿它当闸门，拦下了 73 篇其实
能发的文章；现在**正文超限交给拆分处理**，标题超限交给**裁剪**处理
（64 字符，见 [12-标题裁剪与封面.md](12-标题裁剪与封面.md)），
两个都不再是拒绝理由。

**但更要紧的是另一头**：渲染后的 HTML 里，**只有约 25% 是读者能看到的
字**，剩下四分之三全是标签和内联样式。所以「20000 字符」这个上限，
落到读者那里其实只有 5000 字——这才是「文章太短」的真正来源。

## 三、正文上限能配，也能实测

### 官方字段表不可信

官方文档写 `content` **少于 2 万字符**。实测不是这样：

| 提交长度 | `draft/add` | `draft/get` 读回来 |
| --- | --- | --- |
| 20001 | 成功 | 20005（框架多了 4 个字符） |
| 25000 | 成功 | 一致 |
| 40000 | 成功 | 一致 |
| 65535 | 成功 | 一致 |
| 100000 | 成功 | 100004，一字未少 |

微信既不拒绝，也不截断。探测用的 5 篇草稿已删掉。

所以上限不是平台的限制，而是「一篇草稿该有多长」的选择。

### 换一档上限，语料会变成什么样

`python3 weixin/tools/measure-length.py`（一次渲染，多档上限）：

| 上限 | 读者看到 | 草稿数 | 需要拆的文章 | 最长的一篇 |
| --- | --- | --- | --- | --- |
| 20000 | 约 5000 字 | 1484 | 199 篇 | 20 部分 |
| 40000 | 约 10000 字 | 904 | 125 篇 | 11 部分 |
| **60000（默认）** | **约 15000 字** | **736** | **87 篇** | **7 部分** |
| 80000 | 约 20000 字 | 659 | 65 篇 | 5 部分 |
| 100000 | 约 25000 字 | 623 | 50 篇 | 4 部分 |

草稿数少了，配额也跟着少：全量重刷一次从约 1750 次接口调用降到约 900 次。

### 默认取 60000 的理由

- **读者看到的长度**：60000 字符的 HTML 折合约 1.5 万字，已经是一篇长文；
  原来的 20000 只给读者 5000 字。
- **余量**：实测天花板是 100000（``draft/add`` 收下、``draft/get`` 原样存回，
  后台编辑器也不截断——2026-11-14 账号所有者打开一篇长草稿看过，正文完整）。
  默认不贴着天花板，留一段余量。

> 想更长就把 `--max-length` 调到 80000（659 篇，每篇约 2 万字）或
> 100000（623 篇，每篇约 2.5 万字），重刷一遍即可。

### 怎么改

```bash
# 命令行：一次运行一个上限
python3 -m wechat.cli batch --max-length 80000

# 环境变量：定时任务和批量脚本用这个
export WX_MAX_LENGTH=80000

# 统计也跟着走
python3 -m wechat.cli audit --max-length 80000
```

**上限进了内容指纹**：换上限意味着拆法变了，旧草稿带着旧的切法，必须
重发。所以改了上限之后，`batch` 会把文章当成「有变化」重新推一遍
（`--new-only` 不会重推旧草稿）。上限写错会报错，不会悄悄按另一个数跑。

## 四、切在哪：切点阶梯

正文在 `mdparse` 里已经被解析成块级 AST（`parse()` → blocks → `render()`），
所以切点是现成的。切点按「越靠前越体面」的顺序逐级让位：

| 级别 | 切在哪 | 什么时候用 |
| --- | --- | --- |
| 1 | `##` 标题 | 一节放不下时，往下看它的子节 |
| 2 | `###` 标题 | 同上 |
| 3 | `####` / `#####` / `######` 标题 | 同上 |
| 4 | 段落 | 标题层级用完了 |
| 5 | 表格行 / 代码行 / 列表项 | 单个块本身就超了 2 万字符 |

**切在标题上意味着读者看到的是一个完整的小节**，而不是半句话。

### 标题链

切到子节时，父标题不会被丢掉：它在**每一部分的开头重复一次**。

```text
## 大节
### 小节一
（正文）

## 大节          ← 重复：这一部分接着上一部分讲「大节」
### 小节一
（正文）
```

代价是每部分多几十个字符，换来的是读者一眼知道自己在整篇文章的哪个位置。

### 装箱

切点确定之后，还要决定「哪些块归同一部分」。用的是**贪心装箱**：从小节
开始往后塞，塞到再加就超限就开新的一部分。

两个细节：

- **链接的长度单独算**。参考链接区块的外壳是**每部分付一次**，不是每个块
  付一次。所以装箱时按「链接条目」算，不按「链接区块」算，否则会低估
  好几千字符。
- **每部分的开销要单独预留**。这一部分不是只算正文：它还要付参考链接的
  外壳、分类标签、以及头尾两句衔接语。这些开销**每部分付一次**，而且
  长度随文章而变（标题多长、分类几个），所以预留量是**按文章实算**的，
  不是写死的常数。详见下一节。

装箱完还要**渲染一遍验证**：真的超了就再切一次，而不是把整篇文章丢掉
（见下一节）。

### 预留量为什么不能写死

每个部分除了正文还要付这些：

| 项 | 长度 | 随什么变 |
| --- | --- | --- |
| 参考链接外壳 | 171 | 固定（有链接才有） |
| 分类标签 | 114 ~ 246 | 分类的个数和名字 |
| 开头衔接语 | 143 ~ 189 | 标题长度、部分编号 |
| 结尾衔接语 | 143 ~ 152 | 标题长度 |
| **合计上界** | **758** | |

第一版写死了「预留 400 字符」。**这个数字不够**——真实开销上界是 758。

后果不是「文章稍微长一点」，而是：装箱按 400 预留，装出来的部分渲染后
多了两三百字符，于是**整篇文章被拒绝**。实跑时看到的日志是：

```text
! 已跳过: 第 4 部分渲染后正文 20076 字符，超过上限 20000 字符，已拒绝发布
! 已跳过: 第 5 部分渲染后正文 20094 字符，超过上限 20000 字符，已拒绝发布
! 已跳过: 第 2 部分渲染后正文 20092 字符，超过上限 20000 字符，已拒绝发布
```

超了 76 个字符，一篇 4 万字的文章就这么发不出去。

现在预留量按文章实算（`split.framing_reserve`）：把这一篇文章自己的
分类标签、衔接语头尾、以及固定的外壳长度加起来，再加上一点余量。
全语料 568 篇重新算过：**463 篇全部能拆，0 篇被拒**。

> 为什么不是「统一留 800」？那样也能装下，但每一部分都要白白让出 400 个
> 字符的位置，多出来的部分数是可以避免的。按文章实算，长标题短分类的
> 文章能多装一点，短标题多分类的少装一点。

### 装不下的时候：再切一次

装箱是**估算**，渲染才是**事实**。所以渲染之后还有一道兜底：

1. 装箱按估算切出若干部分；
2. 逐部分真的渲染一遍，看长度；
3. 有部分超了，就**按实测的超出量**把它再切一次；
4. 还是超（说明单块就超了）才拒绝整篇。

第 3 步用实测值而不是估算值来切：如果超了 76 个字符，就把这一部分的
可用空间收 76 个字符重切。最多重切 3 轮。

这样「估算偏了一点点」和「文章真的塞不下」就分开了：前者自己修好，后者
才需要人处理。

## 五、标题与衔接

### 标题

```
原标题（一）
原标题（二）
```

中文数字，全角括号。没有上限——一篇 23 万字符的文章会拆成 13 部分，
标题就是（一）到（十三）。

### 衔接

第 1 部分开头：

```text
全文共 3 部分，这是第 1 部分。
```

第 2 部分开头：

```text
接上文《原标题（一）》。全文共 3 部分，这是第 2 部分。
```

第 2 部分结尾：

```text
（未完待续，下一篇：原标题（二））
```

最后一部分结尾：

```text
（全文完，共 3 部分）
```

没拆分的文章**不加任何衔接语**——没有东西可接。

### 摘要

每部分有**自己的**摘要，取该部分的第一段。全篇摘要贴在每一部分上，
草稿箱里就是一排一模一样的字，读者什么也看不出来。

## 六、参考链接

外链在正文里会被微信去掉锚点，所以渲染层早就把它们降级成末尾的「参考链接」
区块（`render.py` 的 `links_html`）。拆分之后这个机制照旧，**每个部分带
自己用到的链接**——只看第二部分的读者，也能找到第二部分引用的出处。

> 拆成 13 部分时，全文链接会分散在 13 个草稿里，而不是集中在最后一份。
> 这是有意的：每篇草稿自洽。

## 七、账本：一个文章多个键

`out/state.json` 里的键：

| 部分 | 键 | 存什么 |
| --- | --- | --- |
| 第 1 部分 | `database/postgresql-xxx` | `media_id`、`fingerprint`、`parts` |
| 第 2 部分 | `database/postgresql-xxx#2` | 同上 |
| 第 3 部分 | `database/postgresql-xxx#3` | 同上 |

第一部分沿用原来的键（不加后缀），所以**没拆过的文章账本一点没变**，
已建的草稿不会被重建。

`parts` 字段记着这篇文章一共几部分。它让「这个文章建完了吗」可以被判断：

```python
complete = 草稿存在 and 每个 slug#k 都有 media_id
```

没有它的话，一次因为配额中断的批量会留下「第一部分建了、第二部分没建」
的半截文章，而 `--new-only` 会以为它建过了，从此再不处理。

### 文章变短了

文章改短之后可能只需要更少的部分。多出来的草稿会被**删掉**：

```text
draft/delete  ←  多余的部分
```

否则草稿箱里会留着「原标题（三）」这种已经过时的稿子，看起来像现行内容。

## 八、拆不开的情况

只有一种：**某一个块自己就超了上限（默认 6 万字符），而且块内没有可切的
边界**。

（装不下的时候还有一道兜底：按实测的溢出量再切一次。所以走到这一步，
说明已经不是「估错了几个字符」，而是真的有一块塞不进去。）

真实语料里这种情况是 **0 篇**——最极端的是一段 34920 字符的代码块
（能按行切开）和一张 29632 字符的表格（能按行切开）。段落也有上限，
但没有一篇超过 15000 字符。

真遇到时文章被跳过，理由写进 `out/batch-report.json`：

```text
第 1 部分渲染后正文 30080 字符，超过上限 60000 字符，已拒绝发布
提示：这一部分单独放也放不下，只能人工拆得更细
```

**不截断。** 被截断的深度文章比没有文章更糟。

## 九、数字

`python3 -m wechat.cli audit`（2026-11-14，默认上限 60000 字符）：

```text
语料: 569 篇, 33 个分类
正文上限: 60000 字符（渲染后的 HTML，可用 --max-length 改）

闸门（逐层收紧，每层只数上一层放行的文章）:
  标题 <= 64 字符         放行  569  需要裁剪   18   ← 超长不再拦下，改裁剪
  原始正文 <= 60000 字       放行  563  超长    6   ← 超长不再拦下，改拆分
  渲染后 <= 60000 字符       单篇放得下  483  需要拆  80

可发布: 558 篇 (98.1%)，草稿总数 736 篇
  其中需要拆成多篇: 87 篇
  其中拆不开（单块就超限）: 0 篇
  其中只有关掉代码高亮才放得下: 18 篇
  其中正文为空（源文件只剩 front matter）: 11 篇
```

> 旧上限（20000 字符）下同样的语料是「可发布 568 篇、草稿总数 1490 篇、
> 需要拆 197 篇」。草稿数少了 754 篇，配额省一半，读者看到的长文多三倍。
>
> 可发布率从 100% 变成 98.1%，少掉的 11 篇是**正文为空的文章**——源文件
> 里只剩 front matter，做成草稿就是个空壳（标题、分类行、落款，中间没有
> 正文）。它们现在被跳过并记下原因，不再进草稿箱；以前留下的空壳用
> `python3 weixin/tools/prune-empty-drafts.py` 清掉。

拆完的分布：45 篇拆 2 部分、24 篇拆 3 部分，最多一篇拆 7 部分。

> 拆分数字按「无 mermaid 渲染器」估算：图按源码算，比真实流水线偏大，
> 所以**真实的部分数只会更少**，不会更多。

### 实跑结果（2026-11-12）

全量回填跑完，**草稿箱 766 篇**，账本 766 条，`reconcile` 对账零差异：

| 项 | 审计估算 | 实跑 |
| --- | --- | --- |
| 草稿总数 | 784 | **766** |
| 需要拆分的文章 | 108 篇 | **106 篇** |
| 拆不开 | 0 篇 | **0 篇** |
| 因超限被拒 | — | **0 篇** |

差的那 18 篇正是 mermaid 图被渲染成 PNG 之后省下来的地方——审计按源码
长度估，真实流水线里图只是一张 PNG。

> **下一轮（标题裁剪解锁后）** 的目标：草稿箱从 766 涨到约 1490 篇。
> 配额不够一次跑完，靠 `auto-draft --new-only` 的定时任务跨天续跑。

本地渲染产物全量核对（`weixin/tools/check-drafts.py`，不耗配额）：

```text
文章 463 篇，渲染出的部分 765 个
带衔接语的部分: 409
带参考链接区块的部分: 119
超长（>20000 字符）的部分: 0
HTML 不合规的部分: 0
```

### 接口配额

全量回填从「一篇草稿 + 一张封面」变成「每部分一篇草稿 + 一张封面」：

| 项 | 数量 |
| --- | --- |
| 草稿 | 736 |
| 封面 | 736 |
| 正文图 | 约 120 |
| **合计** | **约 900 次** |

微信每日上限 2000 次，所以全量回填**一天就能跑完**（旧上限下要分两天）。
换更大的上限还能更省：80000 → 约 660 篇，100000 → 约 620 篇。

## 十、边界与风险

| 边界 | 说明 |
| --- | --- |
| **上限是工具的选择，不是平台的限制** | API 实测收下 10 万字符且一字不截，后台编辑器也确认过不截断（2026-11-14）。真要更长就调 `--max-length`，真出问题也调小重刷，一行命令 |
| 草稿箱会一下子多出几百篇 | 拆分的代价。每篇都要人工点「发表」 |
| 部分之间没有自动跳转 | 微信草稿不支持跨稿跳转，只有衔接语和标题编号 |
| 每部分的封面 | 有图的文章沿用首图；**没图的用本地生成的封面卡**（色相按 slug 取，带分类与主题）；再不行才用仓库自带默认封面 |
| 「阅读原文」都指向原文页面 | 站点上是完整的一篇，读者可以在那里通读 |
| 标题超长的文章 | **不再发不出去**：按内容裁剪到 64 字符（冒号等分隔符处切），原标题进摘要。见 [12-标题裁剪与封面.md](12-标题裁剪与封面.md) |
| 换上限要重刷 | 上限进了内容指纹，改了就必须重发——旧草稿带着旧的切法。这是有意的：拆法变了，内容就变了 |
