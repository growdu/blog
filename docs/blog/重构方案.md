# growdu.cn 重构方案：知识库 + 二次创作中台

> 本文是**方案文档**，不是给读者看的文章。它定义 growdu.cn 从「个人技术文章集合」
> 升级为「AI 时代系统工程师的知识库与成长工作台」的具体做法，并额外解决一个
> 关键问题：**如何让博客成为视频与公众号二次创作的原始材料**。
>
> 涉及的实现细节以仓库现状为准——文中引用的行号、字段名都是实测过的。

---

## 一、目标与边界

### 1.1 一句话定位

> 构建系统，也构建工程师能力。
> 从 PostgreSQL 内核、分布式系统到 AI 协作实践。

站点要同时服务两类消费：

| 消费方向 | 消费方 | 载体 | 需要的原料 |
| --- | --- | --- | --- |
| **阅读** | 人 | Hexo 站点 | 结构化元数据 + 系列导航 |
| **再创作** | 视频 / 公众号 / 头条 | publish 契约层 | 可切片的事实单元 + 口径约束 + 素材索引 |

**关键判断**：这两件事不能各做一套。博客文章是唯一真相（`docs/`），
二次创作的原料必须是**文章自己携带的结构化元数据**，而不是人工另写一份脚本。

### 1.2 明确不做的事

- 不换渲染框架。理由见 `docs/blog/架构.md`，且 `tools/patch-theme.py` 已 3113 行，
  换框架等于重写全部定制。
- 不删除任何历史 URL。见 §7.4 的 URL 稳定性约束。
- 不为视觉好看牺牲长文可读性。正文宽度、行高、字号优先级高于「科技感」。

## 三、内容模型升级

### 3.1 核心决策：字段只加不重

**已有的 4 个字段直接复用，不新增同义字段**：

| 已有字段 | 位置 | 复用为 |
| --- | --- | --- |
| `difficulty` (1-5) | `contract.py` 白名单 + `post-tldr.ejs` 已渲染 | **难度**（方案的 `level`） |
| `tldr` (≤120 字) | 同上 | **TL;DR**（方案的三行摘要） |
| `description` (≤150 字) | 同上 | **卡片摘要 / OG 描述**（方案的一句话价值说明） |
| `cover` | 同上 | **封面 / OG 图**（方案说不要厚重封面，但小尺寸封面仍需要） |

**方案原稿里的 `estimated_reading_time` 不新增**——`min2read` helper 已按字数实时算，
多一个字段就会有两个真相。

**方案原稿里的 `type` 不映射到 `kind`**——`kind` 的值域是 `("post","video")`
（`contract.py:94`），语义是「这篇是文章还是视频」。新增 `article_type`。

### 3.2 扩展后的 front matter 白名单

`sync-hexo.py` 的 `PASSTHROUGH_SCALAR_FIELDS` 与 `publish/publishkit/contract.py`
的 `PASSTHROUGH_FIELDS` 必须**同步扩**，否则新字段会被契约层静默丢弃。

```python
// 文件：publish/publishkit/contract.py
PASSTHROUGH_FIELDS = (
        // ---- 已有，不动 ----
    "title", "short_title", "tldr", "description",
    "difficulty", "cover", "reprintPolicy", "kind",
    "platforms", "publish_on",
        // ---- 新增：知识库层 ----
    "topic",            # 一级主题，标量
    "series",           # 系列 slug，标量
    "series_order",     # 系列内序号，标量（整数）
    "article_type",     # 文章类型，标量
    "status",           # 内容状态，标量
    "software_version", # 适用版本，标量
    "updated",          # 最后更新日期，标量
        // ---- 新增：列表字段（需同时加进 PASSTHROUGH_LIST_FIELDS）----
    "prerequisites",    # 前置知识
    "related",          # 关联文章 slug
)
```

`PASSTHROUGH_LIST_FIELDS` 目前只有 `('platforms',)`，需扩为
`('platforms', 'prerequisites', 'related')`。

### 3.3 新增字段的取值域

```text
topic           ∈ {postgresql, distributed, networking, os, ai, practice, thinking}
series          ∈ 小写 slug，如 logical-replication / pg-kernel-roadmap
series_order    ∈ 正整数
article_type    ∈ {path-node, source-dive, engineering, essay, translation}
status          ∈ {evergreen, maintained, archive, superseded, draft}
software_version ≤ 60 字
updated         = YYYY-MM-DD
difficulty      ∈ 1..5（已有）
```

### 3.4 主题与系列的映射

**主题**是新的组织层（当前 42 个分类太碎），**系列**是学习单元。

```text
topic: postgresql
  ├── series: pg-kernel-roadmap        （14 章，已有完整 _index.md）
  ├── series: logical-replication       （14 篇，已有，需聚）
  ├── series: mvcc-and-visibility      （4 篇）
  ├── series: wal-and-recovery         （5 篇）
  └── series: performance-tuning       （6 篇）
```

**关键约束：主题与系列只走 front matter，绝不动 `docs/` 目录结构。**
理由见 §7.4——目录结构直接决定 URL。

### 3.5 文章类型

| `article_type` | 用于 | 展示差异 |
| --- | --- | --- |
| `path-node` | 路径节点 | 显式标注「前置 / 下一节」 |
| `source-dive` | 源码深潜 | 显式标注版本、关键文件/函数索引 |
| `engineering` | 工程实战 | 显式标注环境与可复现步骤 |
| `essay` | 观点观察 | 进入「实验室」流 |
| `translation` | 翻译整理 | 显式标注原文、整理范围与增补内容 |

## 四、为二次创作预留的字段

这是本方案相对原重构方案的**核心增量**。

### 4.1 问题

当前视频线的选题库（`aiv/选题库.md`）已经做到了很好的一件事——每期视频都带
「数字与出处」表：

```text
| 陈述 | 出处 | 口径 |
| 发布端默认单解码线程串行处理 | docs/db/.../逻辑复制发布端现状.md | 上游公开机制，可引用 |
| 性能提升 2 到 5 倍 | 作者本人在 openGauss 上本地压测 | 必须带「我在 openGauss 上本地压测」的归因，不得说成官方数据 |
```

**但这份表是手工维护在视频线自己的文件里，和文章是分离的两份。**
文章改了，口播稿的口径表不会跟着改——这就是二次创作的漂移来源。

### 4.2 决策：口径表下沉到文章

**每篇文章自己声明它可以被引用的「事实单元」**，视频线与公众号线都从这里读。

新增两个字段（进白名单）：

```yaml
---
title: "PostgreSQL 逻辑复制的 ReorderBuffer 与事务机制"
topic: postgresql
series: logical-replication
series_order: 3
article_type: source-dive
difficulty: 4
software_version: "PostgreSQL 18 dev"
status: maintained

// ---- 可被二次创作引用的事实 ----
claims:
  - "ReorderBuffer 内存按事务增长，超阈值触发 spill 到磁盘"
    source: "src/backend/replication/logical/reorderbuffer.c"
    attribution: "上游公开源码，可引用"
  - "spill 阈值默认 64MB"
    source: "logical_decoding_work_mem"
    attribution: "上游公开参数，默认值随版本变化，引用时须标版本"
  - "在 32 核机器上并行 apply 吞吐提升 2 到 5 倍"
    source: "作者本人在 openGauss 上本地压测"
    attribution: "必须带归因，不得说成官方数据"
---
```

**结构设计**：`claims` 是「陈述 + 出处 + 口径」三元组。
- `陈述` = 可以在视频/公众号里说的事实
- `出处` = 代码路径 / 参数名 / 压测环境（**可验证的锚点**）
- `口径` = 引用时的措辞约束（这是防 AI 幻觉的关键，也是 aiv 现有做法的沉淀）

**校验规则**（加进 `contract.py` 的 `validate_fields`）：
- `claims` 必须是列表，每项恰好 3 个子键
- `attribution` 非空（口径不允许缺省——没有口径的事实不允许被二次创作引用）
- `source` 非空

**同步给下游**：
- `tools/build-video-pages.py` / aiv 选题脚本：读 `source/_posts/**` 的 `claims`，
  自动生成「数字与出处」表
- 公众号 adapter：把 `claims` 渲染成文末的「本文事实与出处」区块

### 4.3 文章 → 视频/公众号的原料映射

| 文章里的东西 | 视频线怎么用 | 公众号线怎么用 |
| --- | --- | --- |
| `tldr` | 视频开场 3 秒的主钩子候选 | 公众号摘要（digest） |
| `claims` | 口播稿的「数字与出处」表 + 归因红线 | 文末事实区块 + 配图数据来源 |
| `difficulty` | 画面难度标识 | 「阅读难度」标签 |
| `article_type` | 选题优先级（`source-dive` 优先） | 排版模板选择 |
| `software_version` | 字幕里的版本口径 | 「适用版本」提示 |
| `series` + `series_order` | 视频的系列编号与承接口播 | 公众号合集归类 |
| `prerequisites` | 「承接上一期」判定 | 「阅读前需要知道」区块 |
| 正文 mermaid 图 | 画面契约的候选（`aiv` 已有 mermaid 处理） | 直接内联 |
| `cover` | 视频封面候选 | 公众号头图 |

**这样「二次创造」不再是重新写作，而是「重新裁剪」。**

## 五、视觉系统：工程研究台

### 5.1 视觉方向

**深色工程研究台**（不是泛赛博朋克）。理由：源码文章里代码块占比极高
（实测 6614 个代码块 / 4026 张图，分布在 579 篇文章里），深色背景对长代码的
可读性增益是实的，不是风格偏好。

```text
基础背景   深石墨黑 #0d1117 → 深蓝灰 #10161f
主色       冷蓝 #4c9aff
强调色     青绿 #2dd4bf（低面积，仅状态与交互）
正文       偏暖白 #e6edf3
次要文字   #8b949e
分隔线     rgba(255,255,255,.08)
```

**深色为默认，浅色为备选**——但当前 `dark.css` 是「浅色基底 + `body.DarkMode`
覆盖」的写法，反过来做成本高。建议：**先做浅色下的「工程感」精修**，
深色模式作为独立工作项放在 §8 的 P2。

### 5.2 排版规范（可读性优先于风格）

| 项 | 值 | 理由 |
| --- | --- | --- |
| 正文宽度 | **760px**（当前 `.container` 是 1125px，文章卡更宽） | 长文阅读舒适度 |
| 正文行高 | **1.85**（当前 1.6） | 中文长文 |
| 正文字号 | 16.5px | |
| 中文字体 | 系统栈：`PingFang SC / Hiragino Sans GB / Microsoft YaHei / Noto Sans SC` | 不引入 webfont |
| 代码字体 | `JetBrains Mono` → `SF Mono` → `Consolas` → `monospace` | |
| 章节编号 | h2/h3 前置等宽编号 | 「技术感」的低成本来源 |
| 段落间距 | 1.1em | |

**关键**：代码块、路径、函数名、参数名统一用等宽 + 微妙的背景色，
形成「技术文档」而非「博客文章」的观感。这是最低成本的科技感来源。

### 5.3 技术感元素（克制使用）

| 元素 | 用法 | 禁忌 |
| --- | --- | --- |
| 低对比网格背景 | 只在 Hero 与系列页 | 不进正文区 |
| 章节编号 | h2/h3 前缀 `01` `01.1` | 不加装饰图形 |
| 终端感代码块 | 标题栏带三个点 + 语言标签 | 不做花哨动效 |
| 阅读进度条 | 顶部 2px | — |
| 状态点 | 系列页/知识地图的节点状态 | 不加粒子/扫描线 |
| 等宽元信息 | 日期、字数、版本、难度 | — |

**明确避免**：大面积霓虹、自动播放视频背景、粒子效果、抽象数据流装饰、
3D 轮播（当前 `/all/` 与 `/recommended/` 都是）。

### 5.4 CSS 落点

**不要继续往 `patch-theme.py` 里塞 CSS**。该文件已 3113 行，
其中约 14 个 marker 块是往 `my.css` 尾部追加的 CSS 字符串。

新视觉系统的 CSS 应该：
1. 放进 `themes/matery/source/css/tech.css`（新建）
2. 用 **CSS 自定义属性** 定义令牌，在 `my.css` 顶部覆盖：
   ```css
   :root {
     --tech-bg: #0d1117; --tech-fg: #e6edf3;
     --tech-accent: #4c9aff; --tech-accent-2: #2dd4bf;
     --tech-measure: 760px; --tech-leading: 1.85;
     --tech-mono: "JetBrains Mono", "SF Mono", Consolas, monospace;
   }
   ```
3. 令牌被 `my.css` / `post.css` / `matery.css` 引用，实现一处改、全局生效

## 六、信息架构与页面

### 6.1 导航（6 项）

```text
首页  /  知识地图  /  专题与系列  /  探索  /  实验室  /  关于
```

当前 `_config.matery.yml` 的 menu 有 7 项，其中「数据库」是专题页、「分类」「标签」
是数据库字段。按方案原则应替换为知识地图/专题入口。

**兼容性**：`/categories/`、`/tags/`、`/database/` 的 URL **全部保留**

当前 `/all/` 是 1.29MB 的 3D 轮播，579 张卡一次性进 DOM，DCL 1308ms。
新页面的筛选维度：

```text
搜索框（修好 B1 后可用）
主题   全部 / PostgreSQL / 分布式 / 网络 / AI / 底层 / 实践 / 思考
类型   路径节点 / 源码深潜 / 工程实战 / 观点 / 翻译
难度   入门 / 进阶 / 深入
时间   近一年 / 按年份
排序   推荐 / 最新 / 最热 / 最近更新
```

卡片样式（信息密度优先，不用厚重封面）：

```text
[逻辑复制 · 第 03 篇]              [深入]
ReorderBuffer 与事务机制
spill 阈值与内存账本的取舍
42 分钟 · PostgreSQL 18 · 更新于 2026-10-27
```

**实现**：客户端筛选。数据源 = 一份精简的 `explore.json`
（只含筛选需要的字段，不含正文）——**不要用 13MB 的 `search.json` 做筛选**。

### 6.6 文章页

现有文章页已经很扎实（TOC、mermaid 缩放、代码高亮+复制、难度星级、
TL;DR、PV、相关文章、上下篇、打赏、评论、转载声明）。保留骨架，增加：

```text
顶部：面包屑（主题 / 系列）+ 系列位置（第 N / 共 M）+ 难度 + 最后更新
正文前：TL;DR（已有）+ 适合谁读 + 前置知识（新增）
侧栏：目录（已有）+ 系列章节进度（新增）
正文后：本篇结论 + 相关概念 + 下一篇 + 同系列导航（新增）
新增（源码类）：适用版本 + 关键文件与函数索引 + 事实与出处表
```

「事实与出处表」直接渲染 `claims`——这一块让文章页本身成为可核验的，
也是二次创作的原料展示。

## 七、内容治理与迁移

### 7.1 内容审计表

新增 `docs/blog/内容台账.md`（或 `publish/` 侧生成），每篇一行：

```text
slug | topic | series | order | article_type | difficulty | status | cover | claims 数
```

由 `tools/check-content-contract.py` 扩展生成，**不手写**——
手写台账必然与 front matter 漂移。

### 7.2 状态机

```text
evergreen   长期有效，持续维护
maintained  跟随上游版本维护
archive     历史资料，保留可读性，顶部加过时提示
superseded  已被新文章替代，加「建议阅读新版」链接
draft       实验性，不进主导航
```

**不删旧文**。当前 `docs/` 有大量过时内容
（`docs/dpdk/nxp测试报告`、`docs/vpp/fatsup-cpu间转发测试报告`、
`docs/source-tracks/linux/daily-ops/银河麒麟V10 远程桌面`、各种 2018-2022 的工具教程），
删掉会伤已有搜索流量。

### 7.3 优先级

| 优先 | 范围 | 数量 |
| --- | --- | --- |
| P1 | PostgreSQL / 逻辑复制 / 数据库内核系列 | ~60 篇 |
| P2 | 分布式系统、网络、Linux 内核 | ~80 篇 |
| P3 | AI 系列、高考系列、生活观察 | ~100 篇 |
| P4 | 2018-2022 早期技术笔记（多数标 archive） | ~200 篇 |

### 7.4 URL 稳定性（硬约束）

**URL 段直接来自 `docs/` 目录结构**（`tools/sync-hexo.py` 的
`out = os.path.join(POSTS, parent, f'{name}.md')` → `permalink(date, post_path)`）。

所以：

> **主题与系列必须只走 front matter。**
> 任何以「重整目录」为手段的分类合并，都会改变 URL，
> 摧毁 §10 里「高价值文章的自然搜索流量」这个验收指标。

**若确实要动目录**（比如把 `docs/database/` 和 `docs/db/` 合并）：

1. 先导出旧 URL 全表（`docs/` 路径 → permalink）
2. 从 git 历史自动比对路径变更，生成映射
3. **自动生成 redirect**——不要手写 `REDIRECTS` 字典
   （`tools/sync-hexo.py:122` 现在是手写 17 条，579 篇规模下不可持续）
4. 逐条验证 301 生效

### 9.1 各线消费什么

### 9.2 视频线的具体改动

`aiv/选题库.md` 现在手工维护「关联文档 / 数字与出处」两张表。

   选题库的「数字与出处」表

这样 `aiv/选题库.md` 从「事实仓库」降级为「选题决策台」，
