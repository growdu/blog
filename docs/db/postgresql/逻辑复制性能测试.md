可以。这里先把范围**严格限定为一个独立的 PostgreSQL 逻辑复制 Benchmark Suite**，不包含 `pg_replication_trace`，也不依赖任何自研 PostgreSQL Extension。

目标就是先回答一个纯粹的问题：

> **PostgreSQL 18 原生逻辑复制，在不同数据规模、事务规模、并发度、DML 类型、网络条件和 Subscriber 负载下，到底能达到多少复制吞吐，以及瓶颈在哪里。**

# PostgreSQL Logical Replication Benchmark Suite

建议项目名称：

```text
pg-repl-bench
```

版本：

```text
v1.0
PostgreSQL 18
```

---

# 1. 项目目标

Benchmark Suite 主要实现四个目标。

### 目标一：测量逻辑复制吞吐

```text
WAL generation rate
Send rate
Receive rate
Apply rate
End-to-End rate
```

### 目标二：测量复制延迟

```text
Replication Lag
Apply Lag
Catch-up Time
```

### 目标三：定位性能瓶颈

不需要修改 PostgreSQL 源码，利用原生统计接口和 OS 指标判断：

```text
Publisher CPU
Publisher IO
Logical Replication
Network
Subscriber CPU
Subscriber IO
Subscriber Lock
```

### 目标四：建立可重复的性能基线

支持：

```text
PG18 → PG18

不同 workload
不同并发
不同事务大小
不同网络
不同硬件
```

并输出标准化结果，方便横向比较。

---

# 2. 非目标

第一版明确**不做**：

```text
❌ pg_replication_trace
❌ PostgreSQL 内核修改
❌ Logical Decoding 插件
❌ WAL 内部 hook
❌ 单表内部 Decode Trace
❌ Transaction → Relation 精确追踪
❌ 自定义 Apply Worker
```

也就是说：

> **只使用 PostgreSQL 官方提供的 SQL/统计视图 + pgbench + Linux 标准工具。**

# 26. 最核心的 Rate 算法

## WAL Rate

```text
Δpg_current_wal_lsn()
---------------------
       Δtime
```

---

## Send Rate

```text
Δsent_lsn
---------
  Δtime
```

---

## Receive Rate

```text
Δreceived_lsn
-------------
    Δtime
```

---

## Apply Rate

原生 PostgreSQL 下，建议同时采用两种定义：

### LSN-based

根据 Subscriber 的复制位置估算：

```text
ΔLSN / Δtime
```

### Data-based

通过 workload 已知的：

```text
rows
bytes
transactions
```

计算：

```text
applied rows / elapsed time
```

最终两个指标同时报告。

# 27. End-to-End Throughput

定义：

```text
Workload Start
       ↓
第一次产生 change
       ↓
...
       ↓
Subscriber 完成 Apply
```

最终：

```text
E2E throughput =
successfully applied logical data
/
E2E elapsed time
```

# 28. Replication Lag

建议同时报告：

```text

Time Lag
```

LSN：

```sql

    pg_current_wal_lsn(),
    replay_lsn
)
```

```text

```

# 29. Bottleneck 判断

第一版不做复杂 AI，只做规则判断。

### Decode/WAL

```text
WAL Rate 高
Send Rate 明显低
CPU 高
```

→ Publisher/Decoding 疑似瓶颈。

### Network

```text
Send Rate ≈ Network bandwidth
Walsender waiting
Receive Rate ≈ Send Rate
```

→ Network 疑似瓶颈。

### Apply

```text
Receive Rate >> Apply Rate
Subscriber CPU/IO 高
```

→ Apply 疑似瓶颈。

### Lock

```text
Apply Worker
wait_event_type = Lock
```

→ Lock bottleneck。

# 43. 一个非常重要的设计原则

这个 Benchmark Suite **不要试图测“内部 Decode MB/s”**。

因为在不修改 PostgreSQL、不增加 extension 的前提下，原生接口并不能准确提供：

```text
Logical Decode:
xxx MB/s
```

因此 v1.0 应该严格定义：

```text
WAL Generation Rate
Send Rate
Receive Rate
Apply Rate
```

而不是伪造一个：

```text
Decode Rate
```

这是保证 Benchmark 数据可信的关键。

## 45. 最终定位

这个版本的 `pg-repl-bench` 应该是一个**纯黑盒 Benchmark**：

```text
              PostgreSQL 18
                   │
             不修改源码
                   │
          ┌────────┴────────┐
          ▼                 ▼
      Publisher          Subscriber
          │                 │
          └──── Logical ────┘
               Replication
                   │
                   ▼
             pg-repl-bench
                   │
                   ▼
             Performance
               Report
```

它先建立一套**可信的 PostgreSQL 18 原生逻辑复制性能基线**。

后续如果开发 `pg_replication_trace`，则可以变成：

```text
                 pg-repl-bench
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
     Native Metrics          PRT Metrics
          │                         │
          ▼                         ▼
     “复制有多快”              “为什么这么快/慢”
```

这两个项目解耦后，Benchmark Suite 本身即使永远不开发 `pg_replication_trace`，也仍然是一个完整、可独立使用的 PostgreSQL Logical Replication 性能测试工具。
