## 2.1 先看一眼你要面对的东西

## 2.2 编译：踩过的坑和它们的解法

### 2.2.1 先看整条流水线

从源码树到「能写对象的集群」，中间就这四步：

```mermaid
flowchart LR
    A["源码树 /work/cwork/ceph"] --> B["cmake ..<br/>生成 build/CMakeCache.txt"]
    B --> C["make -j nproc<br/>产出 build/bin 与 build/lib"]
    C --> D["make vstart-base<br/>集群真正要用的那批二进制"]
    D --> E["../src/vstart.sh<br/>必须在 build 目录里跑"]
    E --> F["build/data/<br/>配置 + mon + osd 数据目录"]
    F --> G["ceph -s 与 rados put"]
```

### 2.2.2 Ceph 用 CMake，不是 autotools

这是 v22 之后最值得注意的变化。老文章里满地的 `./configure && make` 已经不适用了。

```bash
cd /work/cwork/ceph
mkdir -p build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Debug \
         -DCMAKE_CXX_FLAGS="-O0 -g3" \
         -DWITH_TESTS=OFF
make -j$(nproc)
```

**为什么这么配**：

| 选项 | 作用 | 备注 |
| --- | --- | --- |
| `-DCMAKE_BUILD_TYPE=Debug` | 选 Debug 预设 | Ceph 的 Debug 预设会额外打开断言和更严的检查 |
| `-DCMAKE_CXX_FLAGS="-O0 -g3"` | 关优化、留全量调试信息 | **单步调试必需**；`-g3` 比默认 `-g` 多宏定义 |
| `-DWITH_TESTS=OFF` | 不编译单元测试 | 打开会额外拉 Catch2 和一堆测试目标，编译时间翻倍 |

如果只是读代码、不打算调试，可以换成：

```bash
cmake .. -DCMAKE_BUILD_TYPE=RelWithDebInfo
```

`RelWithDebInfo` 有优化（编译快、跑得快），但**保留调试信息**，
适合「跑起来看看行为」而不是「一行一行跟」。

### 2.2.3 别全量编译

Ceph 全量编译是**以小时计**的（这棵树有 RGW、RGW 的几十个可选后端、
CephFS、MDS、crimson/seastar 等等）。按需编译才是日常：

```bash
make -j$(nproc) ceph-osd        # 只要 OSD
make -j$(nproc) ceph-mon        # 只要 MON
make -j$(nproc) librados        # 只要客户端库
make -j$(nproc) rados           # 只要 rados 命令行
make -j$(nproc) vstart          # 起集群需要的一整套（见 2.3.1）
```

`make vstart` 是个**自定义目标**（`src/CMakeLists.txt:1235`），
它依赖的东西在 `src/CMakeLists.txt:1218` 的 `vstart-base` 里列得很清楚：

```text
vstart-base ← ceph-osd, ceph-mon, ceph-authtool, ceph-conf,
              monmaptool, crushtool, rados
              + cython_rados, ceph-mgr, ceph-exporter（存在才加）
vstart     ← vstart-base
              + cython_rbd, cephfs, cython_cephfs, ceph-mds,
                mgr-dashboard-frontend-build, radosgw, radosgw-admin,
                tracepoint_libraries, ceph-volume-venv-setup, cephadm
```

注意 `vstart` 比 `vstart-base` 多了 `radosgw`、`ceph-mds`、`cephfs` 这些**重目标**。
如果只关心 RADOS 那一层，用 `vstart-base` 就够：

```bash
make -j$(nproc) vstart-base
```

### 2.2.4 关掉你不需要的功能

编译时间的真正大头是可以关掉的。`CMakeLists.txt` 里的 `option()` 大约 80 项，
常用的开关长这样：

```bash
cmake .. \
  -DWITH_RADOSGW=OFF \        # 砍掉对象存储网关（最肥的一块）
  -DWITH_RBD=OFF \             # 砍掉块设备
  -DWITH_CEPHFS=OFF \          # 砍掉文件系统
  -DWITH_MGR=OFF \             # 砍掉管理服务
  -DWITH_CRIMSON=OFF \         # 砍掉实验性的 seastar 版 OSD（默认就是 OFF）
  -DWITH_TESTS=OFF
```

> `WITH_CRIMSON` 默认就是 `OFF`（`CMakeLists.txt:284`），
> `WITH_RADOSGW` 默认 `ON`（`:600`）—— 想省时间先把 RGW 关掉。

依赖装不上是另一道坎。Ceph 自带依赖安装脚本：

```bash
sudo ./install-deps.sh        # Debian/Ubuntu
sudo ./install-deps.sh --install-mgr   # 还要跑 mgr 模块
```

或者直接用官方容器（`Dockerfile.build` 在树根目录）：

```bash
podman build -t ceph-dev -f Dockerfile.build .
```

### 2.2.5 编译产物在哪

CMake 的规矩是**源外构建**（out-of-tree）：

| 路径 | 内容 |
| --- | --- |
| `build/bin/` | `ceph-osd`、`ceph-mon`、`rados`、`ceph` 等可执行文件 |
| `build/lib/` | `librados.so`、`libceph-common.so` 等 |
| `build/src/` | 中间目标文件、`ceph_ver.h`、`ceph_release.h` |
| `build/include/` | 生成的 `config.h`（`acconfig.h`） |
| `build/data/` | **vstart 生成的集群配置与数据**，跑起来之后看这里 |

`build/src/ceph_ver.h` 里是编译时的版本号，`git describe` 之外的
「这棵树到底是什么版本」以它为准。

## 2.3 起一个本地集群：vstart

### 2.3.1 vstart 是什么

Ceph 自带一个「用本地目录当 OSD」的实验台脚本：`src/vstart.sh`（2,222 行）。
它不需要 root，不需要 systemd，不用 LVM，**所有数据都在 `build/data/` 下面** ——
删掉重来只要一个 `-n` 参数。

> **必须在 CMake build 目录里跑。**
> 脚本靠当前目录的 `CMakeCache.txt` 反查源码位置（`src/vstart.sh:60`）：
>
> ```bash
> if [ -e CMakeCache.txt ]; then
>     # Out of tree build, learn source location from CMakeCache.txt
>     CEPH_ROOT=$(get_cmake_variable ceph_SOURCE_DIR)
>     CEPH_BUILD_DIR=`pwd`
> ```
>
> 在源码目录里直接跑 `./src/vstart.sh`，它找不到编译产物，会一路报错。

### 2.3.2 起集群

```bash
cd /work/cwork/ceph/build
MON=1 OSD=3 MDS=0 MGR=1 ../src/vstart.sh -n -d
```

| 环境变量 | 含义 | 默认 |
| --- | --- | ---: |
| `MON` | MON 数量 | 3（`src/vstart.sh:134`） |
| `OSD` | OSD 数量 | 3（`:135`） |
| `MGR` | MGR 数量 | 1（`:137`） |
| `MDS` / `RGW` | MDS / RGW 数量 | 0 |

| 命令行开关 | 含义 | 行号 |
| --- | --- | ---: |
| `-n` | 新建（清掉旧数据重来） | — |
| `-d` | debug：前台跑，日志直接打终端 | — |
| `--msgr1` | 只用 msgr1（老协议） | `:265` |
| `--msgr2` | 只用 msgr2 | — |
| `--memstore` | OSD 用内存后端，不落盘 | `:256` |
| `--crimson` | 用实验性的 seastar 版 OSD 替代 `ceph-osd` | `:268` |
| `--crimson-smp N` | crimson 的 reactor 线程数 | `:287` |

> `MON=1` 是**故意**的：单 MON 时 Paxos 是「自己跟自己表决」，
> 客户端和 OSD 的交互最简单。练 03 章的 MON 时再起 3 个。

### 2.3.3 验证集群真的活了

```bash
ceph -s                        # 集群状态
ceph osd ls                    # OSD 列表
ceph osd dump | head -40       # OSDMap（03、05 章的主角）
rbd pool ls                    # 池列表
rados -p rbd put obj1 /etc/hostname    # 写一个对象
rados -p rbd get obj1 /tmp/out         # 读回来
```

写成功之后，`build/data/` 下面会出现完整的集群状态：

```text
build/data/
├── ceph.conf            # 生成的配置，配置项和真实集群一模一样
├── keyring/
├── asok/                # 各守护进程的 admin socket
├── mon.mon0/            # MON 的 osdmap、membership
├── osd0/ … osd2/        # 每个 OSD 的数据目录（BlueStore）
└── ...
```

**`ceph.conf` 值得通读一遍** —— 它是把「 Ceph 有哪些配置项、默认值是什么」
这个问题一次讲清楚的最好材料（配置项的权威定义在
`src/common/options/*.yaml.in`，见 2.6.4）。

### 2.3.4 拆集群

```bash
../src/vstart.sh --stop       # 正常停
pkill -f ceph-osd             # 或者直接杀
```

`--stop` 也会清掉 admin socket 目录（`src/vstart.sh:741-746`）。
在容器里反复起停时，记得 `vstart` 会去 `redis-cli FLUSHALL`
（`src/vstart.sh:8-14`）—— 如果你本机跑着 redis 且有数据，**先备份**。

### 2.3.5 日志在哪

`-d` 模式下日志直接打终端。跑起来之后（去掉 `-d`），日志在：

```bash
tail -f build/data/ceph-osd.0.log
```

想看更细的日志，调 debug 级别。v22 的 debug 是一套**新机制**：
日志按「子系统」划分，配置项名就是 `debug_<子系统名>`：

```bash
ceph config set osd.0 debug_ms 20      # 消息收发
ceph config set osd.0 debug_osd 20     # OSD 内部
ceph config set mon.a debug_mon 20     # MON 内部
```

- 子系统清单在 `src/common/subsys.h`（`SUBSYS(name, log, gather)` 宏，93 个），
  枚举由 `src/common/subsys_types.h` 从它生成；
- 源码里用 `dout(20) << ...` 打日志，子系统由文件顶部的
  `#define dout_subsys ceph_subsys_osd` 指定（`src/osd/OSD.cc:171-174`）；
- 配置项名的规则写在 `src/common/debug_level_guard.cc:55` 的注释里；
- 调试级别**不在** `src/common/options/*.yaml.in` 里 —— YAML 只管静态配置项；
- v22 还加了保护：debug 级别调得太高会**自动回落**
  （`high_debug_level_threshold` / `high_debug_level_reset_timeout`，
  `src/common/options/global.yaml.in:530` 和 `:545`），避免手一抖把生产集群刷爆。

> **调试级别是 Ceph 的万金油**：任何「它到底走到哪一步」的疑问，
> 90% 的答案是「调高对应的 debug 级别再看一遍」。

## 2.4 代码地图

### 2.4.1 地图一：进程 → 源码入口

每个 Ceph 守护进程都是「一个薄壳 + 一个真正的类」：

| 守护进程 | 入口 | 真正的主体类 | 头文件 |
| --- | --- | --- | --- |
| MON | `src/ceph_mon.cc` | `Monitor` | `src/mon/Monitor.h` |
| OSD | `src/ceph_osd.cc` | `OSD` | `src/osd/OSD.h` |
| MGR | `src/ceph_mgr.cc` | `Daemon` | `src/mgr/Daemon.h` |
| MDS | `src/ceph_mds.cc` | `MDSRank` | `src/mds/MDSRank.h` |
| RGW | `src/rgw/rgw_main.cc` | `rgw::AppMain` | `src/rgw/rgw_main.h` |
| 客户端库 | — | `librados::IoCtxImpl` | `src/librados/IoCtxImpl.h` |

`ceph_osd.cc` 只有几十行，它做的是「解析命令行 → 造 `CephContext` → 造 `OSD` →
交给 `global_init` 跑事件循环」。**真正要读的是那个主体类**，
薄壳永远不值得读。

### 2.4.3 地图三：消息类

v22 起，**每一种协议消息一个类**，全部在 `src/messages/` 下：

```bash
ls src/messages/ | wc -l     # 179
ls src/messages/ | grep -i osd
```

常见的一些：

| 消息类 | 文件 | 什么时候用 |
| --- | --- | --- |
| `MOSDOp` | `src/messages/MOSDOp.h` | 客户端 → OSD 的读写请求 |
| `MOSDOpReply` | `src/messages/MOSDOpReply.h` | OSD → 客户端的回复（带 ACK/ONDISK） |
| `MOSDRepOp` | `src/messages/MOSDRepOp.h` | primary → 副本，复制事务 |
| `MOSDMap` | `src/messages/MOSDMap.h` | MON → 客户端/OSD，OSDMap（全量与增量都在这一个消息里） |
| `MOSDBeacon` | `src/messages/MOSDBeacon.h` | OSD → MON，心跳与状态上报 |
| `MMonGetMap` / `MMonMap` | `src/messages/MMonGetMap.h` | 客户端向 MON 要集群状态 |
| `MMonSubscribe` / `MMonSubscribeReply` | `src/messages/MMonSubscribeReply.h` | 客户端订阅 OSDMap |
| `MMgrOpen` / `MMgrCommand` | `src/messages/MMgrCommand.h` | MGR 与各守护进程的通道 |
| `MMonPaxos` | `src/messages/MMonPaxos.h` | MON 之间的 Paxos 消息 |
| `PaxosServiceMessage` | `src/messages/PaxosServiceMessage.h` | PaxosService 的消息基类 |

**消息类型常量**在 `src/include/ceph_fs.h` 里，命名是 `CEPH_MSG_*`
（例如 `CEPH_MSG_OSD_OP` = 42，`src/include/ceph_fs.h:178`）。

> **老文章踩空点**：v16/v17 时代的 `MSG_OSD_WRITE` 这类枚举**已经不存在了**。
> 现在是两层：消息级 `CEPH_MSG_*`（哪种消息）+ 操作级 `CEPH_OSD_OP_*`
> （消息里装着什么操作）。写请求的实现在 `src/osd/osd_types.h` 的
> `struct OSDOp`，opcode 在 `src/include/rados.h`。

```text
├── mon.yaml.in             # MON
├── mds.yaml.in             # MDS

├── rbd.yaml.in             # RBD
```

**这批 YAML 是 Ceph 的隐藏文档**。想知道 `osd_max_backfills` 到底什么意思、
默认值多少、什么时候可以调，答案就在 `osd.yaml.in` 里 —— 比代码清楚得多。

### 2.4.5 地图五：PG 状态机（提前剧透）

`src/osd/PeeringState.h`（2,935 行）是全仓最该单独认识的文件：
**Ceph 的 PG 状态机是一个 boost::statechart**，状态和事件全在里头。

## 2.5 定位代码：四个工具

30 万行里找一个函数，靠的是工具链，不是记忆力。

### 2.5.1 ripgrep：查文本（默认用这个）

```bash
cd /work/cwork/ceph/src

# 找定义
rg -n 'Objecter::_calc_target' osdc/

# 找调用点（谁用了这个函数）
rg -n '_calc_target' --type cpp

# 找某个字段在哪里被改
rg -n 'pg_mappings' osdc/Objecter.cc

# 排除噪声（二进制、测试）
rg -n 'do_op_impl' -g '!**/test/**' -g '*.cc'
```

`rg` 默认会跳过 `.gitignore` 里的东西，但 Ceph 树里**有些生成文件没被忽略**，
所以 `-g '!**/test/**'` 这类排除条件要常备。

### 2.5.2 ctags：定义跳转


然后在 vim 里：


Ceph 的头文件通常已经把接口、成员、语义注释写全了，
**跳过去先读声明再读实现**，效率比通读实现高一个量级。


### 2.5.4 GDB：运行时

```bash
gdb -p $(pgrep -f ceph-osd | head -1)
```

常用断点（配合 01 章的链路）：

| 断点 | 看什么 |
| --- | --- |
| `OSD::ms_fast_dispatch` | OSD 收到消息的第一站 |
| `PrimaryLogPG::execute_ctx` | 组事务 |
| `BlueStore::_txc_state_proc` | 存储引擎的事务状态机 |

详细姿势见 01 章 §1.13。**两条纪律**：

1. **先跑起来，再打断点**。没跑起来就设断点，debug 目录里的符号和你想的对不上。
2. **一次只跟一条线**。同时下五个断点，栈会把你绕晕；从入口单点进，
   用 `bt` 看清调用者是谁。

挂到运行中的进程需要 `ptrace` 权限。容器里可能要 `--cap-add=SYS_PTRACE`，
或者把 `/proc/sys/kernel/yama/ptrace_scope` 设成 `0`。

### 2.5.5 Ceph 的命名习惯（决定 grep 效率）

| 约定 | 例子 |
| --- | --- |
| 类名 `PascalCase` | `Objecter`、`PrimaryLogPG`、`BlueStore` |
| 方法名 `snake_case` | `handle_op`、`do_transactions`、`_calc_target` |
| 私有成员 `_` 前缀 | `_osdmap`、`_op_queue` |
| 消息类 `M` + 语义 | `MOSDOp`、`MMonGetMap` |
| 操作码 `CEPH_OSD_OP_*` | `CEPH_OSD_OP_WRITE`、`CEPH_OSD_OP_TRUNCATE` |

前向声明在头文件顶部成片出现 —— 想看一个类的全部接口，
先 `rg -n "class BlueStore" os/bluestore/BlueStore.h`，
再看同文件里的其他声明。

## 2.6 运行期观测：admin socket

除了 GDB，每个 Ceph 守护进程还开了一个 **admin socket**，
通过它可以在不中断进程的前提下问它各种问题。

```bash
# 通用入口
ceph daemon osd.0 <command>
ceph daemon mon.a <command>

# 常用命令
ceph daemon osd.0 perf dump          # 事务延迟直方图（最常用）
ceph daemon osd.0 dump_historic_ops   # 历史操作延迟
ceph daemon osd.0 status              # 内部状态
ceph daemon osd.0 help                # 列出这个守护进程支持的所有命令
```

admin socket 的实现是 `src/common/admin_socket.cc`。
vstart 集群里 socket 落在 `build/data/asok/`。

`perf dump` 是调 OSD 性能问题时最该先看的：它给出 apply/commit 延迟的
直方图，能一眼看出是「提交慢」还是「应用慢」。
