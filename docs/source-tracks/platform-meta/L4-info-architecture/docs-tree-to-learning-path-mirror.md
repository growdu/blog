# 把 `docs/` 的目录重排成学习路径的镜像

| 编写人 | 编写时间 | 适用版本 |
| --- | --- | --- |
| growdu | 2026-11-26 | docs/ 590 篇 · 11 条赛道 · 48 个阶段 · 规则表 0 条正则 |

上一篇讲的是**分类树为什么退休**、学习路径为什么不能跟它合并。
那篇写完，分类树没了，但物理目录还在原地：
`docs/` 下 34 个顶层目录，按学科和工具切；学习路径的规则表里 10 条赛道，
按教学顺序切。两套东西各说各的。

这篇讲的是把这两套**合成一套**——让目录长成规则表的形状。

---

## 一、搬家前的样子：目录在替规则猜

规则表要做的事，是把每篇文章归到「某条赛道的某个阶段」。
但目录是按**学科和工具**切的：

```text
docs/db/            docs/distributed/     docs/dpdk/
docs/database/      docs/linux/           docs/vpp/
docs/pgsql/         docs/code/            docs/docker/
docs/ai/            docs/vue/             docs/go_web/
```

赛道是按**教学顺序**切的：

```text
起步与全景 → 存储引擎 → 索引与查询 → 事务与并发 → WAL 与恢复 → 逻辑复制
```

一个说「这篇讲什么」，一个说「这篇该第几个读」。
目录名和赛道名根本不是一回事，所以规则只能写**正则**——
29 条正则，是这种错位留下的疤。

正则有个要命的性质：**失配是静默的**。
文章悄悄从学习路径里消失，首页少一张卡片、少一个阶段条目，
页面本身看着还是完整的 —— 少的那个人不会知道。

作者每加一篇新文章，都得先想清楚「它像不像某篇老文章」，
再写一条正则去凑。规则表于是变成一张没人敢动的表。

## 二、搬成什么样

一句话：

```text
docs/source-tracks/<赛道>/<阶段>/…
```

11 条赛道、48 个阶段：

| 赛道 | 阶段 | 篇数 |
| --- | --- | --- |
| PostgreSQL 源码内核 | 8 | 207 |
| 工程与语言 | 4 | 109 |
| Linux 与网络 | 5 | 65 |
| 分布式与集群 | 4 | 64 |
| 数据面：DPDK · VPP | 4 | 44 |
| AI 与工具 | 4 | 31 |
| 人生与成长 | 4 | 26 |
| 博客与自媒体 | 4 | 20 |
| Ceph 源码 | 2 | 9 |
| 平台元数据 | 6 | 6 |
| Linux 源码 | 3 | 6 |

> 篇数是**搬家当时**的口径：587 篇 `.md` + 3 篇 `.html` = 590。
> 本文自己落地之后，「平台元数据」多一篇，变成 7 篇。

阶段目录带 `L1-`、`L2-` 这样的编号前缀（`L7-logical-replication/`），
因为**顺序本身就是内容** —— 目录名不带序号，
「这条赛道该从哪读起」这件事就得靠翻文档才能知道。

搬完 `docs/` 只剩一个顶层目录：`source-tracks/`。
34 → 1。

## 三、规则表：一条正则都不剩

目录和规则合成一套之后，规则表就只剩下一种表达方式：**路径前缀**。

```text
29 条正则  →  0 条
90 条 path_prefix + 26 条 path_exact  →  60 条 path_prefix + 6 条 path_exact
```

一个阶段目录恰好对应一条 `path_prefix` 规则。
加一篇新文章，做法变成了：**放进对应的阶段目录**。
不用写规则，不用想正则，不用猜它像谁。

剩下的 6 条 `path_exact` 是给视频内容单元的 ——
它们不在 `docs/` 里（住在 `aiv/`），路径固定，走单列规则。

> **「规则表里一条正则都不剩」是这次搬家唯一的验收标志。**
> 只要还剩一条正则，就说明还有某个判断靠猜；
> 而猜错的代价是静默的 —— 文章不见了，页面还是完整的。

## 四、四样跟着一起动的东西

搬目录本身是机械活。真正要小心的是**跟着目录一起走的那四样**。
它们每一件都是「看起来各管各的，其实必须对得上」。

### 4.1 分类链：从 1/2/3 级混着，到清一色 3 级

分类链是构建期算出来的：文章的第一级分类来自它所在的一级目录的
`_index.md` 标题，其余各级来自祖先目录的 `cascade.categories`。

搬家前它是什么样子？

| 链长 | 篇数 |
| --- | --- |
| 1 级 | 223 |
| 2 级 | 96 |
| 3 级 | 271 |

一半多的文章连赛道这一级都没有 —— 因为它当时就躺在一个平铺目录里。
搬完之后，**每一篇**都是 3 级：**内容库 → 赛道 → 阶段**。

链上的分类名也跟着换了一批：从 67 种变成 56 种，
46 个旧的退场，35 个新的进场，21 个沿用。
分类页 2026-11-19 就退休了，所以这些名字唯一的消费者是搜索索引 ——
换个说法，不是丢了一类。

### 4.2 URL：590 篇全变，老地址由 591 条重定向接住

文章换了目录，URL 就换了。重定向表从 320 条长到 591 条。

这里有个容易忽略的点：**老的重定向不能只加不改**。
上一轮搬过的文章，老 URL 是「上一轮的地址」，新一轮的地址是「这一轮的地址」，
中间得**链式归并**成一条线。老链接是别人几十年前的书签，
它只能跳一次，不能跳一次之后再跳一次。

### 4.3 日期：搬家之前逐篇固化

这一条是踩过坑才写进流程的。

站点的文章地址带日期段（`/2023/09/14/...`），
而日期是从 git 提交历史里取的 —— 取的是**这个文件最早的一次提交**。
问题在于：`git mv` 会留下一条「搬家」提交。
如果按提交历史算日期，搬过家的文件会拿到**搬家那一刻**的时间。

590 篇一起搬家 = 590 篇的发布日期集体挪到同一天。
搜索排序、外链、读者的时间线，全乱。

所以搬之前先把每篇的日期固化下来（`data/date-overrides.json`，
590 条），让生成器优先读这张表，而不是回头去猜 git 历史。
固化完再搬，日期才不会跟着搬。

> **这张表自己也踩过同一个坑**：第一版是搬家**之后**才生成的，
> 而脚本从 git 历史里读到的「最早一次提交」已经是搬家那一提交 ——
> 590 条日期齐刷刷写着搬家那一刻。
> 修法是拿搬家前的那个 commit 重取一遍真实日期，
> 再用 `capture-dates.py --check` 逐篇比对钉住。
> 现在实测：逐篇比对 591 篇（590 篇搬过来的 + 本文这一篇），漂移 0 篇。

### 4.4 审校台账：记录跟着文章走

`review/` 下 18 份逐篇审校记录，每份开头一行「原文：docs/<路径>」。

文章搬了家，记录不搬，台账就在审一篇已经不存在的文章 ——
「已审 18 篇」这个数字会变成假话。
所以记录文件本身搬家、开头那行改掉、目录也镜像文章的赛道结构。

> 台账的目录就是分组键：读者按赛道找「这条线审到哪了」，
> 靠的就是 `review/source-tracks/<赛道>/`。
> 记录挂错赛道，那条赛道的进度就少一篇 ——
> 而索引表里那一行还在，数字照样好看。

## 五、代价

**590 篇 URL 全变。** 这是最大的一笔。搜索权重、外链、读者的书签，
全靠重定向接住。老地址跳过去会是**软 404** ——
服务端对任何未知路径返回首页，HTTP 200、页面完整，
探活脚本看起来一切正常。所以「重定向的目标存在」必须被测试钉住，
不能靠肉眼看。

**两个赛道改了名**：`db-internals` → `postgresql`，
`linux-network` → `linux`。学习路径页的地址跟着变，
老地址用别名页接住（`/learning/db-internals/` 仍然能进，
页面上写清正身在哪）。

**站内相对链接是最贵的一课。** 它是唯一一类「旧工具查不出来」的断裂：
不是路径写死了，是「相对于当前文件」这层意思。
写好的工具能查绝对路径，查不出相对路径。

## 六、靠什么验证它没漂回去

搬家是一次性的工程，但上面那四样东西会**继续各自演进**。
规则表会加赛道，重定向表会加条目，分类链会改名字，台账会加记录。

四样东西一旦对不上，读者看到的站点就自相矛盾：

- 规则表说阶段在 `L7-logical-replication/`、目录却在别处 ——
  学习路径页列出来的文章点开是 404；
- 重定向的目标指向一篇不存在的文章 —— 老链接跳过去是软 404，**看起来一切正常**；
- 分类链少一级 —— 分类页少一层，搜索的分类维度跟着歪，而页面上看不出哪里不对；
- 审校记录挂在一条赛道下，原文却在另一条 —— 台账说「这篇审过了」，其实审的是另一篇。

所以这次留了 13 条守卫测试（`tests/test_learning_path_tree.py`），归成六件事：

1. 每条重定向的目标都必须在 `docs/` 里真实存在；
2. 每个阶段目录恰好一条 `path_prefix` 规则，且目录真实存在；
3. 兜底阶段吸收 0 篇（原有守卫）—— 加了新文章就得给它写规则，不许靠兜底蒙混过关；
4. 分类链是三级、每篇文章的链长与链条一致；
5. 每份审校记录的「原文」路径存在，且记录在原文所属赛道的目录下；
6. 赛道配色的类名跟规则表的赛道 id 对得上 —— 改了 id 不改配色，
   那张卡片会退回默认色，**看起来像没配过**。

它们全是**结构对账**，不需要构建产物 —— 所以能进不构建产物的 CI 工作流。
这也是为什么它们守的不是「搬家搬对了」，而是「搬完之后没漂回去」。
