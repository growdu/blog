# 平台元数据

平台元数据 赛道：6 个阶段，由浅入深。

写文章的人通常不写「我的博客是怎么搭的」。这篇站点要补的就是这个洞：
**把平台本身当成内容**——它怎么组织内容、怎么把一份母稿编译成页面、
怎么把同一份内容分发到五个平台、怎么把文章变成视频。

这些内容一直存在，但只以工程文档的形式躺在仓库里，没有一篇进过站点。
工程文档回答的是「怎么改」，这一系列回答的是「为什么这么设计」——
**解决了什么问题、有什么取舍、为什么不用更简单的做法**。

> 这不是自夸。这套东西里大部分决定都是被现实逼出来的：
> 有的是被平台的接口权限逼的，有的是被「日期被 git 搬家改掉」这种事故逼的。
> 把来龙去脉写下来，比贴一份架构图有用得多。

## 六个系列

| 系列 | 讲什么 | 适合什么时候读 |
| --- | --- | --- |
| 平台总览 | 这是什么、三条产线、仓库怎么分层、为什么不用现成方案 | 第一篇，先建立整体印象 |
| 内容模型 | 母稿、内容单元、平台产物；front matter 契约 | 想知道「一份内容怎么变成五个平台的东西」 |
| 构建流水线 | `docs/` → `source/` → `public/`；主题补丁、CI 门禁 | 想改样式、改构建、或者自己搭一套 |
| 多平台分发 | 平台能力模型、发布清单、幂等、调度 | 想把内容发到不止一个平台 |
| 视频生产线 | 视觉分镜契约、渲染引擎、期号与母稿的绑定 | 想知道「代码怎么画出一条视频」 |
| 信息架构 | 分类重构、学习路径、站点 IP 骨架 | 关心「读者怎么在你的站里找到东西」 |

## 怎么读

建议按 **平台总览 → 内容模型 → 构建流水线** 的顺序读：
前三篇是一条线——先知道整体有几个部件，再知道部件之间传递的是什么数据，
最后知道数据怎么被加工成页面。后三篇各自独立，可以按兴趣挑。

六个系列目前各有一篇，都是各自那条线的**开篇**：
先讲清楚那个部件要解决什么问题、为什么这么设计，
再往下才是它内部的细节。

## 一条贯穿全系列的原则

这一系列反复出现同一句话：**入库的是事实，不入库的是产物。**

规范、契约、配置、代码、测试进仓库；图片、音频、成片、构建产物留在本机。
不是为了洁癖，是因为产物**可以被重建**，而事实不能。
把两者混在一起，仓库就会变成一个既不可读、又随时可能与真相不一致的东西。
