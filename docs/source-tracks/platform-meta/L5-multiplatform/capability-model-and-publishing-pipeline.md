# 一份声明顶掉五套 if-else

| 编写人 | 编写时间 | 适用版本 |
| --- | --- | --- |
| growdu | 2026-11-17 | 5 个平台已声明 · 567 条状态快照 · 调度器未上线 |

同一条内容，发到公众号、头条号、抖音、视频号、B 站，
每个平台的形状、限额、自动化程度都不一样。

这篇讲：**怎么把这些差异从代码里抽出来变成数据**，
怎么保证「重复跑一遍不会发两遍」，以及为什么这套系统的自动化
**故意停在半路**。

---

## 一、五套 if-else 长什么样

先把五个平台的真实约束摆出来（都是实测值，后文解释来源）：

| 平台 | 标题 | 正文 | 其他硬约束 |
| --- | --- | --- | --- |
| 公众号 | 64 字 | 60000 字符 | 调用方出口 IP 必须在白名单里 |
| 头条号 | 30 字 | 单段 200 平台字 | 封面 452:352 **横图**、单图 20 MB、webp 可直传 |
| 抖音 | 30 字 | 500 字（编辑预算） | 时长 ≤ 15 分钟、话题 ≤ 5 个 |
| 视频号 | 16 字 | 1000 字 | 标题超限**「保存草稿」按钮直接变灰**、moov 必须前置 |
| B 站 | 79 字 | 249 字 | 标签总长 199 字、关键帧间隔 ≤ 10 秒 |

这些数字如果写进代码，就是五个地方各写一遍判断。
而且它们**会变**——平台改一次规则漏改一个不会报错，
只会在某天发稿时被平台当场拒掉。

---

## 二、把规则变成数据

做法是：每个平台一份声明文件，写清楚它是什么、自动化停在哪、审不审、
限额是多少、媒体规格是什么、用哪个命令去调它。

声明用 TOML，不用 YAML，也不用 Python 常量。三条理由：

- **零依赖。** TOML 解析是 Python 3.11 标准库里的东西，整个发布链路的
  运行时依赖是**零**。这不只是省事：契约层是整条链路的底座，
  不该因为「装依赖失败」而起不来。前置元数据那边甚至为此手写了一个小解析器。
- **数据不是代码。** 平台规则变了改这份文件，不改 Python。
  从「人工出包」升级到「自动建草稿」到「自动发布」，
  升级路径是**改一行 TOML**，不是改一套代码。
- **它是一份会被别人编辑的输入。** 所以每个字段都严格校验：
  必填缺失、类型不对、取值不在域内，一律报错，
  而且消息里带**点号路径**（`limits.title_chars`），不漏出裸的 KeyError。

严格校验不是洁癖。这里出过一次真实事故：有个门槛开关的名字被打错了一个字母，
拼错的那个被当成「未知但无害」放行，真实的那个取默认值——
**「这个平台不需要认证」被静默翻掉了**，而且没有任何一行代码会报错。

所以顶层直接拒绝未知键。名字对不上，当场炸。

---

## 三、闸比平台松 = 错闸

这一节是整套东西里最容易做错的地方。

抖音的作品标题，早先写的是 55 字——那是「常见口径，没实测」。
2026-11-15 在网页后台实测，右边挂的字数计数器是 `0 / 30`。
**平台硬上限是 30 字，比 55 小。**

后果不是「我们被拒了」，是**闸比平台松**：它会放行一条平台当场就拒的稿子，
错误发生在最难受的时刻——内容做好了，点发布，平台说不行。

所以收紧到 30。

反方向的例子是抖音正文：平台上限实测是 1000 字，闸里留的是 500。
这个 500 不是平台规则，是**编辑预算**——正文别把首屏挤掉。
闸比平台严，安全。

头条号正文那条 3000 字同样是编辑预算：平台侧实测根本没有总量上限，
20000 字整段粘进去也不截断。真正的硬约束是**单段** 200 平台字。

公众号那条 60000 字符**不是平台限制**，是工具选的一档：
官方字段表写「少于 2 万字符」，但实测 20001 到 100000 字符全塞进去都成功，
读回来一字未少。选 60000 是因为渲染后的 HTML 里只有约四分之一是读者看得见的字。

还有一条纯经验的：头条号的封面比例是 **452:352，是横图**。
早先按 3:4 竖图切，会把宽图裁成一条窄竖片。

所以每条数字后面都记着两件事：**实测到什么**，以及**还没测到什么**。
「实测了 A」不等于「B 也实测了」——比如头条号正文图上限 3 张，
试点只放了 2 张，那条是运营手册的建议，不是平台限额。

规律是：**硬上限取平台口径（宁可严不能松），编辑预算取我们自己的口径
（可以比平台小）。**

## 四、两个读者，一份真相

同一份声明文件有两个读者：契约层读**任意**平台，平台 adapter 只读**自己**平台。

两份实现**互不 import**——认的是同一份文件，不是同一份代码。

有一份测试专门逐条比对两边的「接受 / 拒绝」结论对不对得上。
九条已经对齐。剩下三条是「一边更严」，方向不同是刻意的：

- 契约层多核对一道「这个平台到底是哪个」——`id` 必须与文件名一致；
- adapter 对限额里的键更严——因为它**读**这些限额，猜得出哪个是拼错了；
  契约层把限额当成不透明的键集合原样保留，不该替它猜字段含义。

原则是：**对同一份坏声明，只要有一个读者拒绝就够了。**
发布流水线走的是契约层这一道闸。

这里也有一个已知缺口：浏览器自动化那一层把视频号和 B 站的限额
硬编码在 Python 里，今天两边数字一致，但没有测试把两者钉在一起。

## 五、加平台 = 加一份声明，不改代码

声明里有一段写明用哪个命令去调这个平台。
契约层就按这条命令去调那个平台的命令行入口，**不 import 它的任何模块**。

依赖方向是双向禁止的：契约层不许 import 任何平台模块，平台也不许 import 契约层。
两边只认「一份声明 + 一份发布清单」这两样纯数据。

这就是「加平台 = 加一份声明，不改代码」的意思——
契约层这一侧确实不用改。但它有个前提：那个平台得有一个能跑的
命令行入口，以及一份属于自己的发布契约。

如果某个平台的文案约束特别多，允许它在自己的目录里带一份自己的切片代码。
视频那三家就是这么干的：**有意的复制，不是偷懒**——各平台的文案约束真的不一样，
视频号拒收标题里的中文逗号、抖音要把三段拼成一个文本发。复制比抽象便宜。

复制出来的那份靠契约测试把形状钉住：三个平台的快照字段集合必须完全相等。
这条守卫一开始只比了两个平台，加进抖音之后改成**遍历全部**——
否则新平台进来时它又变成半个。

## 六、发布清单：另一份纯数据

一个内容单元 × 一个平台 = 一份发布清单。

必填五项：`content_id`、`platform`、`kind`、`title`、`body_html`；
可选四项：摘要、封面、来源地址、素材。未知字段直接拒。

它是**纯数据**：不含时间戳、不含随机数、不含凭据。
同一份清单序列化两次字节一致——所以它可重放、可比对。

超限怎么办？契约层和 adapter 的答案不一样，而且**都是对的**：

- **契约层不截断。** 它只列违规：标题超了多少字、正文超了多少字。
  理由是「截断出来的标题和正文对读者没有意义，反而掩盖问题」。
- **adapter 层截断，但留痕。** 标题在标点处切，正文**在段落边界上**切，
  图片超限就连正文里的占位符一起删掉——不然正文留着「图4」，包里却没有那个文件。
  每一条都写进发布包的人工上传清单，明写「这条被截了」。

公众号是第三个答案：超长文章**分篇**，不是截断——标题里留出位置
给「（一）」「（二）」。

还有一道闸是给人看的：浏览器自动化流程分成「填」和「发」两段。
「发表」是不可逆的外部可见动作，填错了收不回来。
所以填完会留下截图和一份「填了什么」的清单，人能自己看一眼再决定发不发。

## 七、幂等：重复跑一遍不会发两遍

两层键，各管一件事：

- **调度层**用周键。定时任务周五跑一次，同一天手动又跑一次，
  没有周键就会发两篇；而发布层的键拦不住这个——两篇是不同内容单元。
- **发布层**用（内容单元，平台）。同一篇在同一平台发两遍。

视频那边还多一层：内容层的键用的是**成片的哈希值**。
因为视频的「正文」就是成片本身，文案一个字没改但成片换了很常见
（重混音、修关键帧），用元数据的哈希不行。

还有一个容易漏的判定：算「这篇已经发过了」的时候，
**已出包也算**。出包不是「已发布」，但它意味着这篇已经走完流水线了；
不把它算进去，它就会因为「最久未发」每周被选上一次，轮转队列卡死在一篇上。

写盘必须原子：先写临时文件，刷到盘上，再改名。理由很硬——
**半个 JSON 比没有更坏**：读不出来的那份会被当成「什么都没发过」，
于是同一周发两遍。坏状态文件也不吞：改名成 `.corrupt`，字节留作证据。

## 八、调度器：故意停在半路

自动化的档位是三档，而且是数据：

| 档位 | 含义 |
| --- | --- |
| `manual` | 出包 + 人工上传 |
| `api_draft` | 自动生成 + 自动进草稿箱，最后点一下发表由人完成 |
| `api_publish` | 自动发布，轮询审核状态 |

两个平台停在这两档的理由值得说：

- **公众号是 `api_draft`**，因为本号是订阅号、个人主体，
  发表接口实测被回「无权限」。草稿箱天然是审批闸门——
  **这不是失败，是答案**。
- **头条号是 `manual`**，因为账号没认证，开放平台的权限开不了。
  但实测下来**自动存草稿这条路是通的**。
  注意档位描述的是「开放平台 API 权限开到哪一档」，不是「能不能建草稿」——
  这两件事混起来，是这套数据里最容易读错的地方。

顺便说清楚现状：**调度器的非试运行路径从未跑过。**
调度状态文件至今是空对象，状态快照里也没有一条带调度器该写的字段。
代码、测试、模板、定时配置都在，缺的是第一次真跑。

选题规则是「一周一篇，最久未发」。按最新会永远发新文章，
积压的老文章永远轮不到。

还有两条约束：

- **主动发布不写周键。** 否则手动发了一篇，周五就什么都不发，出现空窗。
- **发布动作必须留在固定 IP 的机器上。** 公众号接口要求调用方出口 IP
  在后台白名单里，托管的 CI 环境出口 IP 是动态的，会被全挡下来。

---

## 九、几条不做的事

- **不在缺字段时补默认值。** 补出来的默认值看起来能用，
  但它会让「作者忘了写」变得无声无息。
- **不把三种状态混成一句话。** 「已发布」「已存草稿」「待上传」是三件事，
  含糊地说「已发布」是发布场景里最贵的一种错——
  人会以为发出去了，然后**再传一遍**。
